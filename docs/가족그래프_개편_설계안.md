## 1. 배경 — 왜 바꾸나

현재 `family_members`는 모든 관계가 "피상속인과의 관계" 하나뿐인 **평평한 리스트**다.
구성원끼리의 연결(누가 누구의 자식인지)이 없어서 다음을 표현·판정할 수 없다.

| 못 하는 것 | 근거 |
| --- | --- |
| 대습상속 (먼저 사망한 자녀의 자녀가 대신 상속) | 민법 제1001조 |
| 특별대리인 필요 판정 (미성년 상속인의 친권자가 공동상속인인지) | 민법 제921조 |
| 상속 순위 이동 (1순위 전원 부재 시 2순위로) | 민법 제1000조 |
| 재혼 가정(전혼 자녀), 양자, 사실혼 구분 | — |

또한 가족 정보를 대화에서 추출하지 않고 **초기 진입 시 사용자가 직접 입력**하는
온보딩을 만들기로 했다 (정확도 100%, 대화 UX 부담 제거).

## 2. 결정사항 (2026-08-25)

1. **스키마**: 평평한 리스트 → **persons(노드) + relations(엣지)** 전면 이행.
   GEDCOM(계보 데이터 표준) 모델 참고. **피상속인도 명시적 노드**가 된다.
2. **입력 UI**: 폼 나열이 아니라 **시각적 가족 트리 + 노드 클릭으로 추가**
   (FamilySearch/Ancestry 패턴). 피상속인을 중앙에 배치 — "피상속인 기준 관계"
   혼란을 시각적으로 해소한다.
3. **질문 흐름**: 민법 제1000조 상속 순위 순서대로 묻는 **인터뷰 위저드**
   (배우자 → 자녀 → 직계존속 → 형제자매). 대다수 사용자는 자녀 단계에서 끝난다.
   복잡 케이스 질문("먼저 세상을 떠난 자녀가 있나요?")은 **조건부로만 펼친다**
   (점진적 공개 — 단순 가족은 30초, 복잡한 가족만 깊어진다).
4. **어휘**: 가족관계증명서·안심상속 원스톱 서식의 용어를 그대로 쓴다
   (사용자가 이미 학습한 표현이고, 증명서를 보며 옮겨 적는 시나리오를 지원).
5. **진입 설계**: 초기 온보딩 + **"나중에 할게요" 스킵** + 대화 중 재진입
   (에이전트가 협의·상속인 얘기가 나올 때 입력 화면으로 안내).
6. **호환 경계 유지**: 에이전트가 소비하는 형태 A(`{"heirs": [...]}`)는
   `repository.get_heirs_dict()` 어댑터가 그래프에서 **파생**한다.
   에이전트 코드(heir_navigator/consent.py 등)는 이 개편에서 건드리지 않는다.
7. **불완전성 처리**: 사용자가 모르는 사실(혼외자, 태아, 연락두절)은 어떤 폼도
   못 받는다. "미확인" 상태를 지원하고, 안내문에 "가족관계증명서로 확인된
   상속인 기준" 한정 문구를 붙인다 (기존 가드레일 철학과 일치).

## 3. 목표 스키마 초안

```
persons
  id            PK
  family_graph_id FK
  name          표시용 호칭 (실명 강제 안 함 — "첫째" 허용, 민감정보 최소화)
  is_decedent   피상속인 노드 표시 (그래프당 정확히 1)
  is_alive      생존 여부
  death_date    사망일 (대습상속 판정에 필요 — 피상속인보다 먼저인지)
  birth_date    생년월일 (선택 — 미성년을 파생 계산, 없으면 is_minor 직접 입력)
  is_minor      미성년 (birth_date 없을 때의 직접 입력값)
  status        confirmed | unconfirmed (미확인 상속인)

relations
  id       PK
  from_id  FK persons
  to_id    FK persons
  type     parent_of | spouse_of
  attrs    JSON (법률혼 여부, 친생/양자 등 — 필요해질 때 채움)
```

- "배우자/자녀/손자녀" 같은 관계 명칭은 저장하지 않고 **피상속인 노드로부터의
  탐색으로 파생**한다 (자녀 = 피상속인의 parent_of 역방향 1단계, 손자녀 = 2단계).
- 기존 `family_members` 테이블은 **교체**한다 (현재 데이터가 테스트 3건뿐이라
  이행 부담 없음 — 단, 4-B 결정 필요).

## 4. 상속인 판정 엔진 (신규, 이 개편의 핵심 가치)

그래프는 데이터일 뿐이고, "이 그래프에서 상속인이 누구인가"를 계산하는 엔진이
있어야 그래프가 값어치를 한다. **현재 이 엔진은 존재하지 않는다** —
`family_graph/engine.py`가 빈 껍데기로 자리만 잡혀 있다 (법정상속분 계산도
호출처가 없어 제거된 상태). 관할은 이 파일로 한다 (가족관계 파생 계산, 담당 지원).

v1 범위 제안:

| 기능 | 근거 조문 | 비고 |
| --- | --- | --- |
| 상속 순위 계산 (직계비속 → 직계존속 → 형제자매 → 4촌 방계) | 민법 제1000조 | 4촌 방계는 v1 제외 가능 |
| 배우자 공동상속 / 단독상속 | 민법 제1003조 | |
| 대습상속 | 민법 제1001조 | death_date로 선사망 판정 |
| 특별대리인 필요 판정 | 민법 제921조 | 미성년 상속인의 parent_of가 공동상속인인지 |
| 법정상속분 (배우자 1.5 : 자녀 1) | 민법 제1009조 | tax_calculator의 기존 계산과 단일화 (engine.py 독스트링에 이미 예고된 협의 사항 — 승원 협의) |

- 결격(제1004조)·상속포기 반영은 v1 제외 제안 (포기는 heir_navigator 대화와
  얽혀 범위가 커짐 — 4-C 결정 필요).
- heir_navigator의 절차 데이터(procedure/)와 같은 철학을 적용한다:
  **모든 판정 규칙에 근거 조문 + verified 플래그**, LLM은 판정에 관여하지 않는다.

## 5. 입력화면 흐름 초안

```
[온보딩 진입]
  "돌아가신 분(또는 대비하려는 분)을 기준으로 가족을 알려주세요"
  가운데 피상속인 카드가 놓인 트리 화면

  Step 1  배우자   [있음/없음] → 있음이면 카드 추가 + 생존 여부
  Step 2  자녀     [+ 자녀 추가] 반복 → 카드마다 호칭("첫째" 자동)·미성년
          □ 먼저 세상을 떠난 자녀가 있어요
             → 해당 자녀 카드 아래 [+ 자녀(손자녀) 추가] 열림   ← 대습상속
  Step 3  (자녀가 0명일 때만) 부모님 생존 여부 → (부모도 없으면) 형제자매
  [나중에 할게요]                    [저장하고 시작하기]

[채팅 화면]
  상단 칩 "👨‍👩‍👧 가족 3명" → 클릭 시 트리 편집 화면 재진입
```

- 트리 UI에서 카드 추가 행위 자체가 엣지 입력이 된다 — 사용자는 "관계를
  입력한다"가 아니라 "가족 그림을 그린다"고 느낀다.
- 저장 시 트리 전체를 일괄 전송 (`PUT /family-graphs/{id}` 형태 제안).
- `family_graph_id`는 localStorage 보관, 매 `/chat` 요청에 첨부
  (세션 TTL 2시간에 의존하지 않기 위해).
