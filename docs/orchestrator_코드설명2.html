오케스트레이터 설명

apps/api/orchestrator/ · 사용자 메시지 한 턴을 받아 알맞은 에이전트에게 보내고, 답변을 모아 돌려주고, 다음 턴을 위해 기억하는 모듈

이 서비스에는 에이전트가 여섯 개 있습니다(상속 절차 안내, 유언장 점검, 상속세 계산, 상속분 분석, 자산 정리, 은퇴 설계). 사용자는 그중 누구와 얘기하는지 모르고 그냥 채팅창에 말합니다. 오케스트레이터는 그 메시지를 받아 누가 답해야 하는지 정하고, 그 에이전트에게 지난 대화 맥락을 붙여 보내고, 여럿이 답했으면 하나로 합치고, 다음 턴에 이어갈 수 있게 기억합니다. 아홉 개 파일이 이 일을 나눠 맡습니다.

1. 파일별 설명

router.py — 한 턴의 뼈대

메시지 하나가 들어와서 응답이 나갈 때까지의 순서를 정해 둔 파일입니다. 여섯 단계를 일직선으로 이어 놓고, 각 단계의 실제 일은 담당 파일에 맡깁니다. 오케스트레이터로 들어오는 문은 이 파일의 route() 하나뿐입니다.

세션 읽기 → 에이전트 정하기 → 공유 정보 준비 → 에이전트 실행 → 답변 합치기 → 세션 저장

이 순서를 LangGraph라는 라이브러리로 그래프 형태로 만들어 두는데, 그래프 자체에는 갈림길이 없습니다. "이럴 때는 이쪽, 저럴 때는 저쪽" 같은 판단은 전부 각 단계 안에서 합니다. 그래서 이 파일을 읽으면 무엇이 어떤 순서로 일어나는지는 보이지만, 왜 그 에이전트가 뽑혔는지 같은 건 안 보입니다. 그건 planner.py에 있습니다.

이 파일이 직접 하는 일은 셋입니다.

  • 공유 정보 준비: 가족관계, 재산 정보, 유언장 판정을 세션 값과 이번 요청 값을 합쳐 만듭니다. 이 셋은 어느 에이전트가 뽑히든 전부 받습니다.
  • 최종 응답 조립: 합쳐진 답변에 실행된 에이전트 목록, 에이전트별 원문 전체, 검증 결과를 붙입니다. 이건 프론트로 가는 것입니다.
  • 세션에 뭘 남길지 결정: 실행된 에이전트들의 칸(handoff.py가 출력에서 꺼내 준 조각), 다음 턴에 넘길 에이전트, 사용자 답을 기다리는 에이전트, 최종 답변을 이력에 추가. 이건 서버에 남는 것이고, 위 응답 조립과는 별개입니다.

같은 세션에 요청이 거의 동시에 두 개 오면 둘째는 첫째가 여섯 단계를 다 마칠 때까지 기다립니다. 인메모리 저장소가 저장된 객체를 복사 없이 그대로 돌려주기 때문에, 이 잠금이 없으면 두 요청이 같은 객체를 동시에 고쳐서 응답이 뒤섞였습니다.

def route(payload, *, user_id=None):
    with default_store.turn_lock(payload.session_id):
        result = _compiled().invoke({"payload": payload, "user_id": user_id})
        return result["output"]
받음 main.py에서 요청 본문(세션 id, 메시지, 상담 구분, 가족관계 id 등)과 로그인 사용자 id  ·  보냄 main.py로 최종 응답

session_store.py — 캐비닛 (+ models.py)

대화가 여러 턴에 걸쳐 이어지려면 서버가 "지금 이 사람은 누구와 무슨 얘기 중이었는지"를 기억해야 합니다. 그 기억을 보관하는 캐비닛이 이 파일입니다.

세션 하나에는 이런 것이 들어 있습니다.

  • 에이전트별 칸: 에이전트 이름을 키로 한 딕셔너리. 각 에이전트가 다음 턴에 이어받을 자기 상태(진행 단계, 확정된 슬롯 등). 이 칸을 꺼내고 넣는 규칙은 handoff.py가 맡습니다.
  • 공용 칸: 재산 정보, 유언장 판정, 대화 이력. 특정 에이전트 것이 아니라 모두가 씁니다.
  • 대화 상태: 직전에 답한 에이전트, 다음 턴에 넘기기로 한 에이전트, 사용자 답을 기다리는 에이전트.
  • 소유자: 로그인 사용자 id. 없으면 비로그인 세션.

캐비닛 구현은 두 가지입니다. DB가 없는 환경(로컬, CI)에서는 프로세스 메모리의 딕셔너리, DB가 있으면 Postgres의 sessions 테이블(models.py가 테이블 정의)입니다. 둘 다 "읽기, 쓰기, 만료 정리, 최근 세션 찾기"라는 같은 약속을 지켜서, 오케스트레이터의 나머지 코드는 어느 쪽인지 모릅니다. 서버가 뜰 때 main.py가 DB 주소 유무로 골라 꽂습니다.

class SessionStore:                # 약속
    def load(self, session_id, user_id=None): ...
    def save(self, session_id, state): ...

class InMemorySessionStore(SessionStore): ...   # 딕셔너리
class PostgresSessionStore(SessionStore): ...   # sessions 테이블

읽을 때 세션이 없거나 만료됐거나 남의 것이면 빈 세션을 새로 만들어 줍니다. 남의 세션 id를 찍어 넣어도 내용이 새지 않고 그냥 새 대화가 시작됩니다. 쓸 때도 소유자가 다르면 거부합니다. 읽기만 막으면 빈 상태가 원래 주인의 대화를 덮어써 버리기 때문입니다.

보관 기간은 비로그인 2시간, 로그인 30일입니다. 만료된 세션은 주기적으로 실제로 삭제합니다. 대화 이력은 24개·12,000자 상한이 있고, 넘치면 오래된 것부터 버립니다. 사용자 발화는 앞부분을, 에이전트 답변은 뒷부분을 남깁니다. 에이전트가 던진 질문은 답변 끝에 있어서 앞을 남기면 정작 필요한 문장이 날아갑니다.

받음 router.py에서 세션 id와 요청자 id(읽기), 세션 상태(쓰기)  ·  보냄 router.py로 세션 상태, session_api.py로 사용자의 최근 세션

session_api.py — 캐비닛 창구

session_store와 이름이 비슷하지만 층이 다릅니다. session_store가 캐비닛이면, session_api는 "내 지난 대화 어디 있어요?"라고 물으면 찾아주는 창구 하나입니다. 프론트가 직접 부르는 HTTP 엔드포인트(GET /sessions/mine)이고, 자기 저장 로직은 없습니다.

왜 필요했나. 로그아웃하면 프론트가 세션 id를 버립니다. 서버에는 세션이 30일 남아 있는데 아무도 그걸 가리키지 않으니, 다시 로그인해도 대화가 처음부터 시작됐습니다. 이 창구가 로그인 사용자의 가장 최근 세션을 찾아 세션 id를 돌려주면, 프론트는 그 id로 다음 메시지를 보내고 대화가 이어집니다.

돌려주는 건 화면 복구에 필요한 것만입니다. 세션 id, 대화 이력, 재산·유언장 요약. 에이전트별 칸이나 직전 에이전트 같은 내부 상태는 안 줍니다. 그건 다음 턴에 router.py가 세션 id로 캐비닛을 통째로 꺼낼 때 서버 안에서 살아납니다.
받음 프론트에서 로그인 토큰  ·  보냄 프론트로 최근 세션 id, 이력, 재산·유언장 요약. 없으면 404

planner.py — 누가, 어떤 순서로, 실행

세 가지 일이 한 파일에 있습니다. "이번 메시지에 누가 답할지", "여럿이면 어떤 순서로", "실제로 돌리기". 오케스트레이터에서 판단이 가장 많은 파일입니다.

누가 답할지

원칙은 LLM이 정하고 키워드는 힌트입니다. 각 에이전트 폴더의 spec.py에 적힌 설명과 예시 발화를 registry.py가 모아 주면, 그걸 카탈로그로 만들어 LLM에게 보여주고 "이 메시지는 누가 맡아야 하나"를 묻습니다. 카탈로그와 함께 직전 에이전트, 직전에 에이전트가 던진 질문, 다음에 넘기기로 한 에이전트, 키워드 힌트도 같이 줍니다.

처음엔 반대였습니다. 키워드가 걸린 에이전트만 후보로 놓고 애매할 때만 LLM을 불렀는데, 두 가지 문제가 반복됐습니다. "예금 계좌가 있나요?"라는 질문에 "네, 은행 계좌 하나 있어요"라고 답하면 "계좌"라는 단어 때문에 자산 정리 에이전트가 대화를 가로챘고, 반대로 키워드가 하나도 안 걸리면 LLM이 호출조차 안 돼 직전 에이전트에 붙잡혔습니다. 키워드가 후보를 제한하는 구조 자체가 원인이라 LLM에게 전체를 보여주는 쪽으로 바꿨습니다.

순서는 이렇고, 앞이 뒤보다 우선입니다.

  • 직전 턴에 어떤 에이전트가 사용자 답을 기다리고 있었으면 그 에이전트를 직전 에이전트로 삼아 LLM에게 "이어가기냐 새 주제냐"만 묻습니다. LLM을 못 쓰면 새 주제인지 판단할 수 없으니 그 에이전트를 유지하고 끝냅니다. 키워드 규칙으로 내려가지 않습니다. 단어 하나로 다른 에이전트를 골라 버릴 수 있어서입니다.
  • 아니면 LLM에게 전체 카탈로그를 보여주고 고르게 합니다. 직전 에이전트가 있으면 "이어가기" 선택지를 추가합니다. 한 메시지에 주제가 여럿이면 여러 개를 고를 수 있습니다.
  • LLM을 못 쓰면 키워드 규칙입니다. 넘기기로 한 에이전트가 있으면 그것, 키워드에 걸린 에이전트가 하나면 그것, 없으면 직전 에이전트, 그것도 없으면 상담 구분에 따른 기본, 둘 이상이면 전부 실행.
def classify(user_message, *, pending_handoff, pending_reply_agent, last_agent, ...):
    keyword_hits = registry.match_keywords(user_message)      # 힌트

    if pending_reply_agent is not None:                        # 답변 대기 중
        selected = _llm_route(..., last_agent=pending_reply_agent, pending_reply=True)
        if selected is not None:
            return _plan_from_selection(selected)
        return Plan(path="standard", layers=[[pending_reply_agent]])   # LLM 없으면 유지

    selected = _llm_route(..., last_agent=last_agent, keyword_hits=keyword_hits)
    if selected is not None:
        return _plan_from_selection(selected)

    return _rule_classify(keyword_hits, ...)                   # LLM 없을 때 규칙

어떤 순서로

둘 이상이 뽑히면 층을 나눕니다. 각 에이전트는 spec.py에 "내가 필요로 하는 정보"와 "내가 만드는 정보"를 적어 둡니다. 상속세 계산은 유언장 판정이 필요하고, 유언장 점검은 유언장 판정을 만듭니다. 그래서 둘이 같이 뽑히면 유언장 점검이 앞 층, 상속세 계산이 뒤 층입니다. 서로 무관하면 같은 층입니다. 뽑히지 않은 에이전트가 만드는 정보는 없는 것으로 칩니다. 그래야 상속세 계산만 뽑혔을 때 유언장 점검을 기다리지 않고 바로 돕니다.

실행

층을 앞에서부터 돕니다. 같은 층은 스레드로 동시에 돌립니다. 에이전트는 전부 평범한 동기 함수라서, 병렬은 에이전트가 아니라 여기서 책임집니다. 에이전트마다 입력을 새로 조립하는데, 사용자 메시지, 공유 정보, 대화 이력, 그리고 handoff.py가 꺼내 준 그 에이전트의 칸이 들어갑니다. 앞 층이 있었으면 앞 층 에이전트들의 칸과 답변 원문도 넣습니다. 에이전트 하나가 예외를 던지면 그 자리만 사과 문구로 대체하고 나머지는 계속 갑니다.

받음 router.py에서 사용자 메시지와 세션의 대화 상태  ·  보냄 router.py로 실행 계획(층 목록)과 실행 결과(에이전트별 출력, 갱신된 재산 정보와 유언장 판정)

registry.py — 에이전트 목록의 출처

오케스트레이터 어디에도 에이전트 이름이 하드코딩돼 있지 않습니다. 대신 각 에이전트 폴더에 spec.py를 두고, 거기에 자기소개(이름, 담당 축, 설명, 예시 발화, 키워드, 필요한 정보, 만드는 정보, 실행 함수, 준비 중 여부)를 적습니다. registry.py는 처음 쓰이는 순간 agents 폴더를 훑어 spec.py가 있는 것을 전부 불러들여 등록합니다.

SPEC = AgentSpec(
    name=AgentName.HEIR_NAVIGATOR,
    axes=[AgentAxis.POST_DEATH],
    description="사망 이후 상속인이 밟아야 할 절차를 순서대로 안내하는 에이전트. ...",
    example_utterances=["아버지가 어제 돌아가셨어요. 뭐부터 해야 하나요?", ...],
    keywords=["돌아가셨", "사망신고", "상속포기", "한정승인", "절차"],
    requires=[],
    produces=["procedure_plan"],
    entrypoint=run,
)

이렇게 한 이유는 팀 여섯 명이 각자 에이전트를 만드는 상황에서, 에이전트를 추가할 때마다 오케스트레이터 파일을 고치면 한 파일에서 계속 충돌하기 때문입니다. 자기 폴더의 spec.py만 쓰면 오케스트레이터는 안 건드려도 됩니다. 라우팅 LLM이 읽는 카탈로그도 이 spec.py의 설명과 예시 발화 그대로라서, 라우팅 품질을 좌우하는 건 오케스트레이터가 아니라 각 담당자가 쓴 설명입니다.

키워드 매칭도 여기서 합니다. 메시지에 어떤 에이전트의 키워드가 들어 있으면 그 에이전트를 후보로 돌려줍니다.

받음 agents/*/spec.py  ·  보냄 planner.py로 카탈로그와 키워드 후보, router.py로 이름에 해당하는 실행 함수

handoff.py — 캐비닛 칸을 꺼내고 넣는 규칙

이름은 핸드오프인데 실제로 하는 일의 대부분은 전환과 무관합니다. 하는 일은 딱 세 가지입니다.

  1. 캐비닛에서 그 에이전트 칸을 꺼내 이번 요청 값과 합쳐 에이전트 입력에 넣는다.
  2. 에이전트 출력에서 자기 칸에 넣을 것만 꺼낸다.
  3. 출력에 "handoff:이름" 문자열이 있으면 이름을 읽는다.

104줄 중 절반이 주석이고 함수는 이 셋뿐입니다. DB도, LLM도, 판단도 없습니다.

심사나 검증은 하지 않습니다. 거부하는 일도 없습니다. 모양이 다른 두 곳(세션 저장 형태, 에이전트 입출력 형태) 사이에서 알맞은 조각만 옮기는 역할입니다. 프론트로 보낼 응답을 만드는 것과는 무관합니다. 그건 router.py가 합니다.

개봉. 캐비닛에서 그 에이전트 칸을 꺼내고, 이번 요청에 같은 이름 키로 값이 왔으면 그걸로 덮은 뒤, 에이전트 입력의 자기 이름 키 자리에 넣습니다. 에이전트는 context["heir_navigator"]에서 자기 이전 상태를 봅니다.

def build_agent_context(agent, stored_context, turn_context):
    merged_turn = dict(turn_context)
    namespaced_override = merged_turn.pop(agent.value, {})
    merged_turn[agent.value] = {**stored_context, **namespaced_override}
    return merged_turn

칸에 넣을 것 꺼내기. 에이전트 출력의 data에는 프론트 카드용 정보와 자기 다음 턴용 상태가 섞여 있습니다. 그중 자기 이름 키 아래 하나만 꺼내 줍니다. 이걸 캐비닛에 넣는 건 router.py의 저장 단계고, 프론트로 가는 응답에는 출력 전체가 따로 실립니다.

def extract_state_to_persist(agent, output):
    return dict(output.data.get(agent.value, {}))

핸드오프 신호 읽기. 에이전트가 "다음은 저쪽으로"라고 출력에 "handoff:tax_calculator" 같은 문자열을 담으면 이름을 읽어 줍니다. 형식이 틀리거나 모르는 이름이면 조용히 무시합니다. 실제로 언제 넘길지 정하는 건 planner.py(다음 턴에 힌트로 씀)와 router.py(세션에 기억)입니다.

이 파일이 따로 있는 이유는 "에이전트는 자기 이름 키로 읽고 쓴다"는 약속을 한 곳에 두기 위해서입니다. planner.py와 router.py에 흩어 두면 나중에 한쪽만 고쳐서 어긋날 수 있습니다. 이 약속 덕분에 에이전트 담당자는 세션이 어디에 어떻게 저장되는지 몰라도 되고, 오케스트레이터는 각 칸 안에 뭐가 들었는지 몰라도 됩니다.

받음 planner.py에서 세션 저장 상태와 이번 요청 값, router.py에서 에이전트 출력  ·  보냄 planner.py로 에이전트에 넘길 입력, router.py로 캐비닛에 넣을 상태와 핸드오프 대상

compose.py — 답변 합치기와 숫자 검증

한 턴에 에이전트가 둘 이상 답했을 때 그것을 한 편으로 만드는 파일입니다. 하나만 답했으면 원문을 그대로 쓰고 이 파일은 사실상 아무것도 안 합니다.

여럿이면 LLM에게 합성을 시킵니다. 각 에이전트 답변을 블록으로 묶어 넘기고 "금액·퍼센트·날짜·법률 판정은 한 글자도 바꾸지 말 것"을 규칙으로 줍니다. 그런데 이건 프롬프트 약속이라 LLM이 안 지켜도 걸러낼 방법이 없습니다. 상속세 금액이 틀리면 안 되는 서비스라, 합성문의 숫자를 코드로 다시 검증합니다.

검증 방법: 합성문에서 금액, 퍼센트, 날짜를 정규식으로 뽑아 각각이 원본(모든 에이전트의 답변과 데이터)에 있는지 봅니다. 문자열로 안 찾아지면 값으로 한 번 더 비교합니다. "3억 5천만원"과 "350,000,000원", "2026-02-28"과 "2026년 2월 28일"처럼 표기만 다른 경우를 구제하기 위해서입니다. 양쪽이 명확히 파싱될 때만 같다고 인정하고, 파싱이 안 되면 불일치로 봅니다. 틀린 숫자를 내보내는 것보다 멀쩡한 합성문을 버리는 쪽이 낫다는 판단입니다.

draft = llm_synthesize(agent_outputs, user_message)
if not draft:                                    # LLM 못 씀 → 원문 이어붙이기
    return fallback_concat(agent_outputs), VerificationResult(ok=True, mode="concat")

verified = verify_numbers(draft, agent_outputs)  # 코드 검증
if not verified.ok:                              # 하나라도 원본에 없음 → 합성문 폐기
    return fallback_concat(agent_outputs), VerificationResult(ok=False, ...)
return draft, verified

불일치가 하나라도 있으면 합성문을 버리고 각 에이전트 답변을 소제목 붙여 이어 붙입니다. 그리고 "검증 실패" 표시를 함께 보내 프론트가 확인필요 배지를 띄우게 합니다.

받음 router.py에서 에이전트별 출력과 사용자 메시지  ·  보냄 router.py로 최종 답변과 검증 결과

llm_policy.py — LLM 스위치

오케스트레이터는 LLM을 두 군데서 씁니다. 에이전트 고를 때와 답변 합칠 때. 둘 다 LLM 없이도 돌아가는 폴백(키워드 규칙, 원문 이어붙이기)이 있습니다. 이 파일은 환경변수 하나로 "LLM을 쓸지, 실패하면 조용히 폴백할지 시끄럽게 죽을지"를 정합니다.

  • off 안 씀. 항상 폴백.
  • on 쓰되 실패하면 조용히 폴백.
  • auto(기본) API 키가 있을 때만 on.
  • required 실패하면 폴백하지 않고 예외. 키가 없으면 서버가 아예 안 뜸.

required가 생긴 이유는 키가 빠진 채 규칙 폴백으로 조용히 열화된 상태에서 데모한 사고 때문입니다. 같은 이유로 헬스체크 응답에 "쓰려는데 키가 없음" 상태를 따로 노출합니다. 원래 planner.py와 compose.py에 각각 있던 같은 판단을 한 곳에 모은 파일입니다.

받음 환경변수  ·  보냄 planner.py, compose.py로 LLM 사용 여부와 실패 시 예외 여부, main.py로 헬스체크 상태

2. 사용 흐름

사용자가 채팅창에 메시지를 보낸 순간부터 응답이 돌아올 때까지입니다.

0. 서버가 뜰 때
main.py
DB 주소가 있으면 세션 캐비닛을 Postgres로 갈아끼웁니다. 없으면 인메모리 기본값이 그대로 쓰입니다. LLM 설정이 required인데 키가 없으면 여기서 기동이 실패합니다. 만료 세션 정리 배치를 15분 주기로 띄웁니다. 에이전트 목록 수집은 아직 하지 않고, 첫 요청에서 처음 필요할 때 합니다.
1. 요청 도착
main.py → router.py
요청 본문과 로그인 여부(토큰이 유효하면 사용자 id, 아니면 없음)를 들고 router.py로 들어옵니다. 이 세션의 잠금을 잡습니다(인메모리일 때만).
2. 세션 읽기
router.py → session_store.py
세션 id로 캐비닛에서 이전 상태를 꺼냅니다. 없거나 만료됐거나 남의 것이면 빈 세션입니다. 비로그인으로 시작한 세션인데 지금 로그인돼 있으면 이 자리에서 계정에 붙입니다. 이번 발화를 이력 끝에 넣습니다. 이렇게 먼저 넣어 두면 뒤에서 "마지막 어시스턴트 발화"가 곧 직전 턴의 질문이 됩니다.
3. 누가 답할지
router.py → planner.py → registry.py, llm_policy.py, LLM
세션의 직전 에이전트, 넘기기로 한 에이전트, 답변 대기 에이전트, 대화 이력을 planner.py에 넘깁니다. planner.py는 registry.py로 키워드를 먼저 보고(첫 요청이면 이때 spec.py 수집), 답변 대기 중인 에이전트가 있으면 LLM에게 이어가기/새 주제만 묻고, 아니면 전체 카탈로그를 보여주고 고르게 하고, LLM을 못 쓰면 키워드 규칙으로 정합니다. 둘 이상이면 층을 나눕니다. 결과는 "누구를 몇 층으로"가 담긴 계획입니다.
4. 공유 정보 준비
router.py
가족관계는 요청에 직접 담겨 왔으면 그것, 아니면 id로 DB 조회. 재산 정보는 세션 값에 요청 값을 덮어 병합. 유언장 판정은 요청 값이 실제 점검 결과일 때만 교체. 이 셋이 이번 턴 모든 에이전트에 들어갑니다.
5. 에이전트 실행
router.py → planner.py → handoff.py → agents/*/agent.py
계획의 층을 앞에서부터 돕니다. 에이전트마다 handoff.py가 캐비닛에서 자기 칸을 꺼내 이번 요청 값과 합쳐 입력에 넣고, 공유 정보와 이력을 붙이고, 앞 층이 있었으면 그 결과도 붙입니다. 실행 함수는 registry.py가 spec.py에서 가져온 것입니다. 같은 층은 동시에 돌리고, 하나가 죽으면 그 자리만 사과 문구로 대체합니다. 층이 끝나면 에이전트가 돌려준 재산 정보를 병합하고 다음 층으로 갑니다.
6. 답변 합치기
router.py → compose.py
하나면 원문 그대로. 여럿이면 LLM 합성 → 숫자 검증 → 통과면 합성문, 불일치면 원문 이어붙이기와 확인필요 표시. 그 뒤 router.py가 최종 응답을 조립합니다. 대표 에이전트는 마지막에 실행된 것, 에이전트별 원문은 별도 목록으로.
7. 세션 저장
router.py → handoff.py → session_store.py
실행된 에이전트마다 handoff.py가 출력에서 자기 칸에 넣을 것을 꺼내 캐비닛에 넣습니다. 핸드오프 신호를 낸 에이전트가 있으면 다음 턴 대상으로 기억합니다. 마지막 에이전트를 직전 에이전트로 기록하고, 최종 응답이 "사용자 답을 기다린다"는 신호였으면 그 에이전트를 답변 대기로 기억합니다. 최종 답변을 이력에 붙이고 캐비닛에 씁니다.
8. 응답 반환
router.py → main.py → 프론트
잠금을 놓고 최종 응답을 돌려줍니다. 프론트는 답변을 말풍선에, 에이전트별 원문을 카드에, 검증 실패면 확인필요 배지를 그립니다.
main.py ─▶ router.py
   ├ 2. 세션 읽기 ──── session_store.py
   ├ 3. 누가 답할지 ── planner.py ← registry.py(spec.py 카탈로그) · llm_policy.py · LLM
   ├ 4. 공유 정보 ──── 가족관계 · 재산 · 유언장 판정
   ├ 5. 실행 ───────── planner.py ← handoff.py(칸 개봉) → agents/*/agent.py
   ├ 6. 합치기 ─────── compose.py (LLM 합성 → 숫자 검증)
   ├ 7. 저장 ───────── handoff.py(칸에 넣을 것 꺼내기) → session_store.py
   ▼
main.py ─▶ 프론트

3. 흐름 밖에서 쓰이는 것

  • session_api.py — 재로그인 직후 프론트가 한 번 부릅니다. 최근 세션 id를 돌려주면 프론트는 그 id로 다음 메시지를 보내고, 2단계부터 이어갑니다.
  • 만료 정리 배치 (main.py → session_store.py) — 15분마다 만료된 세션을 실제로 삭제합니다. 예전에는 조회할 때 무시만 하고 행은 영구히 남았는데, 비로그인 대화의 사망일과 재산 정보가 계속 쌓인다는 뜻이라 지우는 쪽으로 바꿨습니다.
  • 헬스체크 (llm_policy.py → main.py) — LLM을 쓰려는데 키가 없어 규칙 폴백으로 도는 상태를 밖에서 알아채기 위한 것입니다.
  • models.py — Postgres 캐비닛이 쓰는 sessions 테이블 정의. DB 마이그레이션 도구도 이 파일을 봅니다.
  • 테스트 전용 — 특정 에이전트만 가짜로 바꿔 끼우는 표(router.py), 목록 초기화(registry.py), 각 팀이 "내 spec이 프롬프트에 실리는가"를 검사할 때 쓰는 별칭(planner.py).
  • __init__.py — 진입점과 캐비닛 교체 함수 두 개만 밖으로 노출합니다.
