# 2026 금융 AI Challenge 기능명세서 — 작성 양식 (팀 공용)

> 공식 양식(첨부2)의 5개 필수 항목에 우리 내용을 채운다. 각자 담당 부분을 이
> 파일에 먼저 채우고 → 팀장이 hwpx로 옮긴다.
>
> **원칙: 배포 URL에서 실제로 동작하는 것만.** 미구현·예정은 5번 "제한사항"에만.
> 프론트 개발 기준표로도 쓴다 — 2번의 "관련 화면" 열 + 3번 흐름 = 지원 빌드/검증 체크리스트.

| 2 | 주요 기능 목록* | 기능 단위로 **기능명 / 기능 설명 / 관련 화면 / 구현 상태** |

| 5 | MVP 검증 방법* | 심사자 확인 절차 / 테스트 계정·샘플 입력·예상 결과 / 실행환경·브라우저 제한 / MVP 제한사항 |

## 1. MVP 구현 범위 * — 팀장 취합

각자 2번에 채운 걸 팀장이 3~5줄 개조식으로 요약.

> (예) 생전/사후 두 여정의 상속 설계를 대화형으로 제공. 로그인 → 상담 구분 →
> 가족관계 입력 → 대화. 대화 중 질문 의도를 분류해 담당 에이전트가 답하고,
> 여러 주제는 하나로 합성하며 숫자를 원문과 대조 검증한다. …

## 3. 사용자 이용 흐름 * — 지원 초안, 각자 자기 기능 진입점 보완

1. 배포 URL 접속 → 회원가입 / 로그인
2. 상담 구분 선택: "지금 준비 중"(생전) / "가족을 떠나보낸 뒤"(사후)
3. 가족관계 입력 (배우자·자녀·부모 생존 여부)
4. 대화 시작 (예: "…")
   - 4a. 시스템이 질문 의도를 분류해 담당 에이전트로 라우팅
   - 4b. 여러 주제면 여러 에이전트 병렬 실행 → 하나의 답변으로 합성 + 숫자 검증
5. 결과 확인: 좌측 대화 / 우측 재산·유언 상태 패널 / 근거 카드(신호등·세액표·분배표)
6. 후속 질문에 선택지 버튼으로 응답 → 재계산

## 4. AI 및 데이터 처리 방식 * — 정민 + 각자 자기 에이전트 한 줄

- **AI 역할**: 질문 의도 분류(라우팅) · 자연어에서 금액·조건 추출 · 여러 답변을
  하나로 합성 · (선택) 유언장/안심상속 조회결과 이미지 판독. **요건·세액·유류분
  판정은 규칙 기반 코드**, 생성형 AI는 계산하지 않음
- **사용 데이터**: 민법·상속세법 규칙, 대법원 판례 N건(법령정보센터 링크 포함),
  안심상속 절차·기한 정보
- **입력 데이터**: 사용자 발화(자연어), 가족관계, 재산·부채 금액, (선택) 이미지
- **출력 데이터**: 합성 답변(마크다운), 유언 요건 판정, 예상 세액 내역,
  법정상속분·유류분, 절차 타임라인
- **개인정보·민감정보**: 유언장 이미지·성명은 **마스킹 후에만** LLM 전송, 원문
  미저장 / 이미지 판독 직후 폐기 / 가족관계·재산정보는 로그인 사용자 계정에 귀속

## 5. MVP 검증 방법 * — 지원 주도

- **테스트 계정**: (회원가입 후 이용 / 또는 심사용 계정 제공)
- **샘플 입력값** — `docs/데모_시나리오_0830.md` 값으로 통일:
  - 시나리오 A(사후): 예금 3,200만원 / 부동산 3억 5천만원 / 대출 1억 2천만원 → 순자산 2억 6,200만원
  - 시나리오 B(생전): 예금 8천만원 / 아파트 5억 → 순자산 5억 8천만원
- **확인 절차(심사자용, 단계별)**:
  1. 로그인 → 상담구분 → 가족관계 …
  2. "…" 입력 → 유언 신호등이 …로 표시
  3. "…" 입력 → 예상 상속세 …원 / 신고기한 …
  4. …
- **예상 결과**: 각 단계별 기대 화면
- **실행 환경 / 브라우저**: 최신 Chrome·Edge, **PC 화면 우선**(모바일 레이아웃 미대응)
- **MVP 제한사항**:
  - 배우자+자녀 / 배우자 단독 상속 외 가족관계는 "전문가 검토 필요"로 안내
  - retirement_planner(은퇴 설계)는 데모 범위 외
  - 유류분은 1차 시뮬레이션 (실제 청구 가능액 아님)
  - 숫자 검증(verify_numbers)은 LLM 합성 사용 시에만 동작

## A-1. `decedent_estate` — 유언 요건 점검 (담당: 정호)

**① 입력 / 출력**

| 방향 | 내용 |
|---|---|
| 입력 | 유언장 유형·내용 서술(자연어) / 유언장 사진(`image_base64`) / 선택지 답변(`context.will_type` 등) |
| 출력 `data.decedent_estate` | `requirements`: 요건별 `{id, name, grade(GREEN·RED·YELLOW·WHITE·PENDING), body(화면 문구), precedents:[{case_no, summary}]}` · `pending_questions`(선택지 버튼) · review/prepare 모드별 안내 문구 |
| 세션 공유 출력 `will_status` | `{checked, will_type, no_will, overall_grade(green·yellow·red), has_effect}` → tax_calculator·heir_share_analyzer가 재질문 없이 참고 |

**② 적용 규칙·법령**
- 민법 제1066조(자필증서에 의한 유언) — 5요건: 전문 자서 · 연월일 · 주소 · 성명 · 날인
- 민법 제1067조(녹음에 의한 유언)
- 판정은 **룰 엔진**(`rules/requirements.json`)이 수행. LLM은 텍스트에서 값 추출(날짜 문자열, 주소·성명 유무)만 담당하고 **판례를 생성·인용하지 않음**
- grade 규칙: GREEN(요건 확인, 판례카드 0) / RED(무효 방향 확립 판례, 카드 1) / YELLOW(사실관계 따라 갈림, 카드 2) / WHITE(법정 요건 아님, 예: 간인) / PENDING(텍스트로 판별 불가)

**③ 판례 근거** (`rules/precedents.json` — 검증된 목록에서만 인용)

| 판단 | 사건번호 |
|---|---|
| 연·월만 쓰고 일(日) 없는 자필유언 무효 | 2009다9768 |
| 주소 없음/동(洞)만 기재 시 무효 | 2012다71688 |
| 워드 작성본·복사본은 자필증서 아님 / 지장(무인)도 날인 인정 / 봉투 기재 주소도 인정 | 97다38510 |
| 날인 없이 서명만 있으면 무효 | 2006다25103, 25110 |
| 무인이 본인 것인지 다투어지면 무효 | 2005누1600 |

**④ 한계·미지원**
- 전문(全文) 자서 판별은 텍스트/사진으로 불가 → **항상 사용자 확인**
- 유언 5방식 중 자필·녹음만 상세 판정 (공정증서·비밀증서·구수증서는 개요 안내)
- 유언장 사진 다중 페이지 미지원 · 간인 실제 날인 여부는 텍스트로 판별 불가
- `"20260503"` 같은 순수 숫자 연속 날짜 미지원
- 상세: `agents/decedent_estate/docs/known_limitations.md`

**⑤ 데모 시나리오 동작**
- **시나리오 A-8**: "자필로 쓴 유언장이 있는데 효력이 있나요?" → 선택지 "직접 손으로 쓴 유언장" → 자서·날인·주소·연월일 요건별 신호등 + 관련 판례 사건번호 카드
- **A-9**: "유언장 효력도 다시 보고 상속세도 다시 계산" → decedent_estate → tax_calculator 순차 실행, 합성 답변
- **시나리오 B-7**: "자필 유언장을 쓰려는데 형식이 궁금해요" → prepare 모드 자필증서 요건 체크리스트

## A-2. `asset_organizer` — 자산·부채 정리 (담당: 정호)

**① 입력 / 출력**

| 방향 | 내용 |
|---|---|
| 입력 | 자산·부채 자연어("예금 3,200만원, 아파트 3억 5천만원") / 안심상속 조회결과 캡처 이미지 / 조회결과 위저드 입력 |
| 출력 `data.asset_organizer` | 확정 자산·부채 목록 · 카테고리별 확인 상태 · 순자산 · `pending_questions`(빠진 카테고리) |
| 세션 공유 출력 `financial_profile` | `{real_estate_value, financial_assets, other_assets, total_debts}` → tax_calculator·heir_share_analyzer·heir_navigator가 재사용 |

**② 적용 규칙·법령**
- 법령 판정 없음 — **사실 정리 도구**
- 카테고리 체크리스트: 예금 / 주식 / 펀드 / 부동산 / 자동차 / 퇴직연금 / 보험 / 부채
- 자산 유형은 화이트리스트로 관리, 목록에 없는 유형은 "기타"로 보존 (버리지 않음)
- **"조용한 실패 금지"**: 정규식·LLM 모두 금액을 확정 못 하면 0으로 채우지 않고 재질문 (보험은 예외 — 금액 없이도 진행)
- 퇴직연금은 확인되면 수령 방식(연금형/일시금)을 한 번 후속 질문

**③ 판례 근거** — 없음

**④ 한계·미지원**
- 자산 유형 화이트리스트 수동 관리
- 이미지 판독 정확도는 사진 품질에 의존
- 개별 재산 감정평가는 하지 않음 (사용자 입력값 그대로)

**⑤ 데모 시나리오 동작**
- **시나리오 A-5 / 5a**: "안심상속 원스톱 조회결과부터 정리하기" 위저드 → 예금 3,200만원 / 부동산 3억 5천만원 / 대출 1억 2천만원 → 순자산 **2억 6,200만원**, 우측 패널 "상속재산 요약"(자산 3억 8,200만원 · 부채 1억 2,000만원)
- **A-5b**: 📷 조회결과 캡처 이미지 업로드 → AI가 판독해 같은 체크리스트에 반영
- **시나리오 B-4 / 4a**: "자산 정리" 타일 → "예금 8천만원, 아파트 5억, 대출 없어요" → 순자산 5억 8천만원

## A-3. `tax_calculator` — 상속세 시산 (담당: 승원)

**① 입력 / 출력**

| 방향 | 내용 |
|---|---|
| 입력 | 세션 `financial_profile` 재사용 + 슬롯 질문: `decedent_is_resident`, `spouse_exists`, `children_count`, `spouse_is_sole_heir`, `original_inherited_property`, `debts`, `financial_assets`, `financial_debts`, `prior_gifts_to_heirs/non_heirs`, `spouse_actual_inheritance` · 세션 `will_status` 참고 |
| 출력 `data.tax_calculator` | `status`(collecting·calculated·unsupported·needs_review) · `last_result`(= `InheritanceTaxResult`): `total_inherited_property`, `deductible_expenses`, `taxable_inheritance_value`, `total_inheritance_deduction`, `inheritance_tax_base`, `tax_rate_percent`, `calculated_inheritance_tax`, `filing_tax_credit`, `estimated_tax_due`, `estimated_filing_deadline`, `warnings` |
| 세션 공유 출력 | `tax_estimate` |

**② 적용 규칙·법령**
- 상속세 및 증여세법

**④ 한계·미지원**

## A-6. 오케스트레이터 (라우팅·합성·검증) (담당: 정민)

**① 입력 / 출력**

| 방향 | 내용 |
|---|---|
| 입력 `AgentInput` | `session_id`, `user_message`, `axis`(pre_need·post_death), `family_graph_id`, `context`, `image_base64` · 세션 상태(에이전트별 컨텍스트, `financial_profile`, `will_status`, 직전 핸드오프) |
| 출력 `ChatResponse` | `reply`(합성 답변) · `agents`(이번 턴 실행된 에이전트, 실행 순서) · `path`(fast·standard·full) · `verification:{ok, mode, mismatches}` · `data`(에이전트별 병합) · `financial_profile` · `will_status` |

**② 적용 규칙** (법령 아님 — 오케스트레이션 로직)
- **라우팅 3갈래** (`classify`): Fast Path(직전 턴 핸드오프 대상) / Standard(키워드 후보 0~1개) / Full Pipeline(키워드 후보 2개 이상 → LLM이 필요한 것만 골라 DAG 병렬·순차 실행 → 합성)
- LLM을 못 쓰는 환경에서는 키워드 후보 전부를 그대로 실행
- **답변 합성 + 숫자 검증** (`compose` / `verify_numbers`): 2개 이상 에이전트면 LLM이 하나의 답변으로 다듬음 → `verify_numbers`가 금액·퍼센트·날짜를 원문과 정규식으로 대조 → 하나라도 안 맞으면 합성본 버리고 각 에이전트 원문 이어붙이기 + "⚠️ 확인필요" 배지. 에이전트 1개면 원문 그대로
- **무재질문**: `financial_profile`·`family_graph`·`will_status`를 세션에 붙여 에이전트 간 공유

**③ 판례 근거** — 없음

**④ 한계·미지원**
- `verify_numbers`는 문자열 대조라 같은 값 다른 표기("1억 2천만원" vs "120,000,000원")를 오탐할 수 있음
- LLM 미사용 시 `verify_numbers` 미실행 (이어붙이기는 원문 그대로라 `ok=True`)
- `decedent_estate`·`heir_navigator`가 같은 턴에 실행되면 겹치는 평면 키(`pending_questions` 등)를 나중 값이 덮어씀 *(수정 예정)*

**⑤ 데모 시나리오 동작**
- **시나리오 A-9**: "유언장 효력도 다시 보고 상속세도 다시 계산해줘" → `path=full`, decedent_estate → tax_calculator 순차, 헤더 "</> 개발자" 켜면 실행 경로·숫자 검증 결과 노출
- **전 시나리오**: 재산·가족관계·유언장 판정을 재질문 없이 이어받음(무재질문)
