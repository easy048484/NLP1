오케스트레이터 설명

apps/api/orchestrator/ · 사용자 메시지 한 턴을 받아 알맞은 에이전트에게 보내고, 답변을 모아 돌려주고, 다음 턴을 위해 기억하는 모듈

  1. 파일별 역할과 로직
  2. 사용 흐름: 메시지 하나가 지나가는 길
  3. 흐름 밖에서 쓰이는 것들

1. 파일별 역할과 로직

흐름에 등장하는 순서대로 놓았습니다. 각 파일은 "무슨 역할인지", "그 역할을 어떤 로직으로 해내는지", "시작할 때 뭘 받고 끝날 때 뭘 보내는지"로 설명합니다.

router.py — 한 턴의 뼈대

역할

메시지 하나를 처리하는 전체 순서를 정의하고, 각 단계를 담당 파일에 맡긴 뒤 결과를 이어 붙입니다. 오케스트레이터의 유일한 진입점입니다.

로직

한 턴을 여섯 단계로 고정하고, 이 순서를 LangGraph라는 라이브러리로 일직선 그래프로 만들어 둡니다. 그래프 자체에는 갈림길이 없습니다. 갈림길은 각 단계 안에서 처리합니다.

세션 읽기 → 에이전트 정하기 → 공유 정보 준비 → 에이전트 실행 → 답변 합치기 → 세션 저장
  • 세션 읽기: 세션 저장소에서 이전 대화 상태를 가져옵니다. 비로그인으로 시작한 대화를 로그인한 채 이어가면 이 자리에서 그 계정 것으로 붙입니다. 이번 사용자 발화를 대화 이력 끝에 먼저 넣어 둡니다. 이렇게 해 두면 뒤 단계에서 "마지막 어시스턴트 발화"가 곧 직전 턴의 질문이 됩니다.
  • 에이전트 정하기: planner.py에 맡깁니다. 세션에 있던 직전 에이전트, 핸드오프 예정, 답변 대기 상태, 대화 이력과 요청의 상담 구분을 넘깁니다.
  • 공유 정보 준비: 가족관계, 재산 정보, 유언장 판정 세 가지를 세션 값과 이번 요청 값을 합쳐 만듭니다. 가족관계는 요청에 직접 담겨 왔으면 그것, 아니면 요청이나 세션에 있는 id로 DB에서 조회합니다. 재산 정보는 요청에 값이 있는 필드만 세션 값을 덮습니다.
  • 에이전트 실행: planner.py에 맡깁니다.
  • 답변 합치기: compose.py에 맡긴 뒤, 최종 응답 객체를 조립합니다. 대표 에이전트는 마지막에 실행된 것, 답변은 compose 결과, 에이전트별 원문은 따로 목록으로, 실행 경로와 검증 결과도 함께 담습니다.
  • 세션 저장: 실행된 에이전트마다 자기 상태를 세션에 넣고, 핸드오프 신호가 있으면 다음 턴 대상으로 기억하고, 마지막 에이전트가 "사용자 답을 기다린다"고 했으면 그 사실도 기억하고, 최종 답변을 이력에 붙인 뒤 저장소에 씁니다.

같은 세션에 요청 두 개가 거의 동시에 오면 둘째는 첫째가 여섯 단계를 다 마칠 때까지 기다립니다. 인메모리 저장소가 저장된 객체를 복사 없이 돌려주기 때문에, 이 잠금이 없으면 두 요청이 같은 객체를 동시에 고쳐 응답이 뒤섞였습니다.

받는 것 main.py에서: 요청 본문(세션 id, 사용자 메시지, 상담 구분, 가족관계 id, 이미지 등)과 로그인 사용자 id
보내는 것 main.py로: 최종 응답(답변, 실행된 에이전트 목록, 에이전트별 원문, 경로, 검증 결과)

session_store.py — 턴 사이에 남는 것 (+ models.py)

역할

대화가 여러 턴에 걸쳐 이어지도록 "지금 어느 에이전트와 대화 중인지"와 "각 에이전트가 이어받아야 할 상태"를 보관합니다. 어디에 보관하는지(메모리인지 DB인지)는 나머지 오케스트레이터가 모르게 감춥니다.

로직

세션 하나에 들어 있는 것: 에이전트별 상태(에이전트 이름을 키로 한 묶음), 모든 에이전트가 공유하는 재산 정보와 유언장 판정, 대화 이력, 직전 에이전트, 다음 턴에 넘길 에이전트, 답변을 기다리는 에이전트, 소유자, 보고 있던 가족관계 id.

저장소는 두 종류이고 같은 약속(읽기, 쓰기, 만료 정리, 최근 세션 찾기)을 지킵니다.

  • 인메모리: 프로세스 안의 딕셔너리. DB 없는 환경(로컬, CI)의 기본값. 세션 id마다 잠금을 하나씩 두어 같은 세션의 동시 요청을 줄 세웁니다.
  • Postgres: sessions 테이블 하나. 테이블 정의는 models.py에 있습니다. 컬럼은 세션 id, 소유자, 가족관계 id, 직전 에이전트, 핸드오프 예정, 에이전트별 상태(JSON), 생성·수정·만료 시각입니다. 재산 정보·유언장 판정·이력·답변 대기 에이전트는 컬럼을 새로 만들지 않고 JSON 안의 _shared라는 예약 키 아래에 같이 넣습니다.

읽을 때: 세션이 없거나 만료됐거나 남의 것이면 빈 세션을 새로 만들어 돌려줍니다. 남의 세션 id를 찍어 넣어도 내용이 새지 않고 그냥 새 대화가 시작됩니다. 저장된 값 일부가 깨져 있으면 그 필드만 비우고 나머지는 살립니다.

쓸 때: 기존 세션의 소유자가 다르면 저장을 거부합니다. 읽기만 막으면 빈 상태가 원래 주인의 대화를 덮어쓰기 때문입니다. Postgres는 같은 세션의 첫 저장이 동시에 두 번 들어와 충돌하면 한 번 더 시도하고, 존재하지 않는 가족관계 id는 비워서 저장이 실패하지 않게 합니다.

보관 기간: 비로그인 2시간, 로그인 30일. 만료된 세션은 주기적으로 실제로 삭제합니다.

대화 이력 상한: 메시지 24개, 전체 12,000자. 넘치면 오래된 것부터 버립니다. 사용자 발화는 앞 2,000자만, 에이전트 답변은 뒤 800자만 남깁니다. 에이전트 답변은 질문이 끝에 붙으므로 뒤를 남겨야 합니다.

받는 것 router.py에서: 세션 id와 요청자 id(읽기), 세션 상태(쓰기)
보내는 것 router.py로: 세션 상태. session_api.py로: 사용자의 가장 최근 세션

planner.py — 누구를, 어떤 순서로, 실제 실행

역할

이번 메시지에 어느 에이전트가 답할지 정하고, 여럿이면 실행 순서를 짜고, 실제로 실행합니다. 세 가지 일이 한 파일에 있습니다.

로직 1. 어느 에이전트가 답할지 정하기

기본 원칙은 LLM이 정하고, 키워드는 힌트입니다. 판단 재료는 각 에이전트 폴더의 spec.py에 적힌 설명과 예시 발화입니다. 이걸 registry.py를 통해 모아 카탈로그로 만들고 LLM에게 보여줍니다.

순서는 다음과 같고, 앞이 뒤보다 우선입니다.

  1. 사용자 메시지에 각 에이전트의 키워드가 들어 있는지 봅니다. 결과는 나중에 힌트로 씁니다.
  2. 직전 턴에 어떤 에이전트가 사용자 답을 기다리고 있었다면, 그 에이전트를 "직전 에이전트"로 삼아 LLM에게 묻습니다. LLM은 "직전 질문에 답하는 중"이면 이어가기를, "명백히 새 주제"면 다른 에이전트를 고릅니다. LLM을 못 쓰거나 실패하면 새 주제인지 판단할 수 없으니 그 에이전트를 그대로 유지하고 끝냅니다. 아래 키워드 규칙으로 내려가지 않습니다. 키워드 규칙은 단어 하나로 다른 에이전트를 고를 수 있어 진행 중인 답변을 보호하는 목적에 맞지 않기 때문입니다.
  3. 그렇지 않으면 LLM에게 묻습니다. 후보는 등록된 에이전트 전부(준비 중 표시가 된 것만 제외)입니다. 프롬프트는 두 부분입니다.
    • 고정 부분: 에이전트 카탈로그(이름, 담당 축, 설명, 예시 발화 앞 3개)와 판단 규칙. 턴마다 같아서 캐시됩니다. 규칙의 핵심은 "사용자가 직전 질문에 답하고 있으면, 답 안에 다른 에이전트의 단어가 섞여 있어도 이어가기를 골라라"입니다.
    • 턴마다 바뀌는 부분: 상담 구분, 직전 에이전트, 답변 대기 여부, 직전 어시스턴트 발화의 끝 500자, 핸드오프 예정, 키워드 힌트, 그리고 사용자 메시지.
    직전 에이전트가 있으면 선택지에 "이어가기"를 추가합니다. LLM은 한 메시지에 주제가 여럿이면 여러 개를 고를 수 있습니다. 응답에서 모르는 이름이나 후보 밖 이름은 버립니다. 하나를 골랐으면 단일 실행, 둘 이상이면 로직 2로 넘어갑니다.
  4. LLM을 못 쓰면 키워드 규칙으로 내려갑니다. 핸드오프 예정이 있으면 그 에이전트. 키워드에 걸린 에이전트가 하나면 그것. 하나도 없으면 직전 에이전트, 그것도 없으면 상담 구분에 따른 기본(사후는 절차 안내, 생전은 자산 정리), 그것도 없으면 절차 안내. 둘 이상이면 전부 실행합니다. LLM 없이는 고를 수 없기 때문입니다.

LLM 호출이 실패했을 때 폴백할지 예외를 낼지는 llm_policy.py의 설정을 따릅니다.

로직 2. 여럿일 때 층으로 나누기

각 에이전트는 spec.py에 "내가 필요로 하는 정보"와 "내가 만들어내는 정보"를 적어 둡니다. 예를 들어 상속세 계산은 유언장 판정을 필요로 하고, 유언장 점검은 유언장 판정을 만듭니다. 같이 뽑힌 에이전트 중 A가 만드는 것을 B가 필요로 하면 A를 앞 층, B를 뒤 층에 둡니다. 서로 무관하면 같은 층입니다. 뽑히지 않은 에이전트가 만드는 정보는 없는 것으로 칩니다. 그래서 상속세 계산만 뽑히면 유언장 점검을 기다리지 않고 바로 돕니다. 의존이 순환이면 남은 것을 한 층에 몰아넣고 경고를 남깁니다.

로직 3. 층 단위로 실행하기

층을 앞에서부터 하나씩 돕니다. 한 층 안에서는:

  • 에이전트마다 입력을 새로 조립합니다. 사용자 메시지, 공유 정보(가족관계, 재산, 유언장 판정), 대화 이력, 그리고 그 에이전트 전용 상태입니다. 전용 상태는 handoff.py의 규약대로 세션에 저장된 이전 상태와 이번 요청이 보낸 값을 합친 것입니다. 앞 층이 있었으면 앞 층 에이전트들의 상태와 원문 답변도 함께 넣습니다.
  • 층에 에이전트가 하나면 그냥 호출하고, 둘 이상이면 스레드로 동시에 호출합니다. 에이전트는 전부 동기 함수라서, 병렬은 에이전트가 아니라 여기서 책임집니다.
  • 에이전트 하나가 예외를 던지면 그 자리만 사과 문구로 대체하고 나머지는 계속 갑니다.
  • 층이 끝나면 에이전트가 돌려준 재산 정보를 공유 값에 병합하고, 유언장 판정이 새로 나왔으면 교체합니다. 다음 층은 이 갱신된 값을 받습니다.
받는 것 router.py에서: 사용자 메시지와 세션의 대화 상태(정하기), 계획과 공유 정보와 에이전트별 저장 상태(실행)
보내는 것 router.py로: 실행 계획(경로 등급과 층 목록), 실행 결과(에이전트별 출력, 병합된 재산 정보와 유언장 판정)

registry.py — 에이전트 목록의 출처

역할

어떤 에이전트가 있는지, 각각 무엇을 하고 어떤 키워드와 의존성을 갖는지를 한 곳에서 제공합니다. 오케스트레이터 코드 어디에도 에이전트 이름이 하드코딩돼 있지 않은 이유입니다.

로직

각 에이전트 폴더에 spec.py를 두고 그 안에 자기 선언(이름, 담당 축, 설명, 예시 발화, 키워드, 필요한 정보, 만드는 정보, 실행 함수, 준비 중 여부)을 적어 두면, 이 파일이 처음 쓰이는 순간 agents 폴더를 훑어 spec.py가 있는 패키지를 전부 불러들여 등록합니다. 한 에이전트의 불러오기가 실패해도 그것만 건너뜁니다. 새 에이전트를 붙일 때 오케스트레이터를 고칠 필요가 없게 하려는 구조입니다.

키워드 매칭도 여기서 합니다. 메시지에 어떤 에이전트의 키워드가 부분 문자열로 들어 있으면 그 에이전트를 후보로 돌려줍니다.

받는 것 agents/*/spec.py의 선언
보내는 것 planner.py로: 전체 에이전트 목록과 키워드 매칭 결과. compose.py로: 제목용 설명. router.py로: 이름에 해당하는 실행 함수

handoff.py — 에이전트와 주고받는 데이터의 규약

역할

에이전트가 오케스트레이터와 상태를 주고받는 형태를 정합니다. 에이전트 담당자는 이 규약만 지키면 오케스트레이터 내부를 몰라도 세션에 자기 상태가 자동으로 남습니다.

로직

  • 네임스페이스: 에이전트는 입력 context에서 자기 이름 키 아래의 값을 읽고, 출력 data에 자기 이름 키 아래에 값을 써서 돌려줍니다. 오케스트레이터는 그 값을 그대로 세션에 넣었다가 다음 턴에 다시 넣어 줍니다. 에이전트끼리 키가 충돌하지 않고, 오케스트레이터는 내용을 몰라도 됩니다.
  • 입력 조립: 세션에 저장된 이전 상태 위에 이번 요청이 같은 이름 키로 보낸 값이 있으면 그것으로 덮습니다. 사용자가 이번 턴에 명시적으로 답한 값이 우선입니다.
  • 핸드오프 신호: 다른 에이전트로 넘기고 싶으면 출력에 "handoff:에이전트이름" 문자열이나 구조화된 핸드오프 목록을 담습니다. 형식이 틀리거나 모르는 이름이면 조용히 무시합니다. 잘못된 신호 하나가 오케스트레이터를 죽이면 안 됩니다.
받는 것 planner.py에서: 세션 저장 상태와 이번 요청 context. router.py에서: 에이전트 출력
보내는 것 planner.py로: 에이전트에 넘길 context. router.py로: 세션에 저장할 상태와 핸드오프 대상

compose.py — 답변 합치기와 검증

역할

한 턴에 여러 에이전트가 답했을 때 그것을 한 편의 답변으로 만들되, 숫자와 날짜가 원문과 달라지지 않았음을 코드로 보장합니다.

로직

  1. 에이전트가 하나면 원문을 그대로 씁니다. 검증할 것이 없습니다.
  2. 여럿이면 LLM에게 합성을 시킵니다. 각 에이전트 답변을 설명과 함께 블록으로 묶어 넘기고, "금액·퍼센트·날짜·법률 판정은 한 글자도 바꾸지 말 것, 없는 내용을 넣거나 빼지 말 것"을 규칙으로 줍니다. LLM을 못 쓰면 이 단계를 건너뜁니다.
  3. 합성문이 나오면 코드로 검증합니다. 합성문에서 금액, 퍼센트, 날짜를 정규식으로 뽑아 각각이 원본(모든 에이전트의 답변과 데이터)에 있는지 봅니다.
    • 1차: 공백과 쉼표를 지운 문자열이 원본에 포함되는지.
    • 2차: 1차에 실패하면 값으로 비교합니다. "3억 5천만원"과 "350,000,000원", "2026-02-28"과 "2026년 2월 28일"처럼 표기만 다른 경우를 구제합니다. 합성문이 연도를 생략한 것은 허용하고, 합성문이 연도를 새로 붙였으면 원본에도 연도가 있어야 합니다.
    • 단위도 쉼표도 없는 짧은 정수("3개월"의 3)는 검증 대상에서 뺍니다. 양쪽이 명확히 파싱될 때만 값으로 인정하고, 파싱이 안 되면 불일치로 봅니다. 틀린 숫자를 통과시키는 것보다 멀쩡한 합성문을 버리는 쪽이 낫다는 판단입니다.
  4. 하나라도 불일치면 합성문을 버리고 각 에이전트 답변을 소제목을 붙여 그대로 이어 붙입니다. 이때 "검증 실패" 표시를 함께 보내 프론트가 확인필요 배지를 띄웁니다. LLM을 못 써서 처음부터 이어 붙인 경우는 원문 그대로이므로 검증 통과로 표시합니다.
받는 것 router.py에서: 에이전트별 출력 목록과 사용자 메시지
보내는 것 router.py로: 최종 답변 문자열과 검증 결과(통과 여부, 어떤 방식이었는지, 불일치 목록)

llm_policy.py — LLM을 쓸지 말지

역할

환경변수 하나로 오케스트레이터가 LLM을 쓸지, 실패하면 조용히 폴백할지 시끄럽게 죽을지를 정합니다. planner.py와 compose.py에 따로 있던 같은 판단을 한 곳에 모은 것입니다.

로직

설정값동작
offLLM을 안 씁니다. 항상 키워드 규칙과 이어 붙이기.
onLLM을 시도하고, 실패하면 조용히 폴백.
auto (기본)API 키가 있을 때만 on과 같음.
requiredLLM을 시도하고, 실패하면 폴백하지 않고 예외를 냅니다. 데모·운영용. 키가 없으면 서버가 아예 안 뜹니다.

required가 생긴 이유는 키가 빠진 채 규칙 폴백으로 조용히 열화된 상태에서 데모한 사고 때문입니다. 같은 이유로 헬스체크 응답에 "쓰려는데 키가 없음" 상태를 노출합니다. 라우팅 분류만 다른 모델로 돌리는 설정도 여기 있습니다.

받는 것 환경변수
보내는 것 planner.py, compose.py로: 쓸지 여부와 실패 시 예외 여부. main.py로: 헬스체크 상태

session_api.py — 재로그인하면 이어보기

역할

로그아웃했다가 다시 로그인한 사용자가 지난 대화를 이어갈 수 있게 합니다. 턴 처리와는 별개의 HTTP 엔드포인트입니다. 같은 폴더의 router.py는 한 턴을 처리하는 파이프라인이고, 이 파일은 FastAPI 라우터라서 이름이 헷갈리기 쉽습니다.

로직

로그아웃하면 프론트가 세션 id를 버립니다. 서버에는 세션이 30일 남아 있는데 아무도 그것을 가리키지 않아 다시 로그인해도 대화가 처음부터 시작됐습니다. 가족관계는 별도 조회로 되찾아지는데 대화 맥락만 유실되는 비대칭이 있었습니다. 이 엔드포인트가 로그인 사용자의 가장 최근 세션을 찾아 세션 id, 대화 이력, 재산 요약, 유언장 요약을 돌려줍니다. 프론트는 그 세션 id로 다음 메시지를 보내면 됩니다. 비로그인 사용자는 쓸 수 없습니다. 떠나면 남지 않는 것이 원칙이라 되찾을 대상이 없기 때문입니다.

받는 것 프론트에서: 로그인 토큰
보내는 것 프론트로: 최근 세션 id와 이력, 재산·유언장 요약. 없으면 404

2. 사용 흐름: 메시지 하나가 지나가는 길

사용자가 채팅창에 메시지를 보낸 순간부터 응답이 돌아올 때까지입니다. 단계마다 어느 파일이 일하는지와 갈림길을 적었습니다.

0. 서버가 뜰 때 (요청 전에 이미 정해지는 것)

main.py

환경변수를 읽습니다. DB 주소가 있으면 세션 저장소를 Postgres로 갈아끼우고, 없으면 인메모리 기본값이 그대로 쓰입니다. 이 순간 이후 오케스트레이터의 나머지 코드는 어느 쪽인지 모릅니다. LLM 설정이 required인데 키가 없으면 여기서 기동이 실패합니다. 만료 세션 정리 배치를 15분 주기로 띄웁니다. 에이전트 목록 수집은 아직 하지 않고, 첫 요청에서 처음 필요할 때 합니다.

1. 요청 도착

main.py → router.py

요청 본문(세션 id, 사용자 메시지, 상담 구분, 가족관계 id, 이미지 등)과 로그인 여부(토큰이 있고 유효하면 사용자 id, 아니면 없음)를 들고 router.py의 진입점을 부릅니다. 진입점은 이 세션의 잠금을 잡고 여섯 단계를 시작합니다.

갈림길: 저장소 종류인메모리면 세션 id별 잠금으로 같은 세션의 동시 요청을 줄 세웁니다. Postgres면 잠그지 않습니다.

2. 세션 읽기

router.py → session_store.py

세션 id로 이전 상태를 가져옵니다.

갈림길: 세션 상태없거나 만료됐거나 남의 것이면 빈 세션을 새로 만듭니다. 있으면 그것을 씁니다.

비로그인으로 시작한 세션인데 지금 로그인돼 있으면 이 자리에서 계정에 붙입니다. 이번 발화를 이력 끝에 넣습니다.

3. 누가 답할지 정하기

router.py → planner.py → (registry.py, llm_policy.py, LLM)

세션의 직전 에이전트, 핸드오프 예정, 답변 대기 에이전트, 대화 이력과 요청의 상담 구분을 planner.py에 넘깁니다. planner.py는 먼저 registry.py로 키워드 매칭을 합니다. 첫 요청이라면 이때 모든 에이전트의 spec.py가 수집됩니다.

갈림길 A: 직전 턴에 답을 기다리던 에이전트가 있나있으면 그 에이전트를 직전 에이전트로 삼아 LLM에게 묻습니다. 이어가기면 그 에이전트, 새 주제면 다른 에이전트. LLM을 못 쓰거나 실패하면 그 에이전트를 유지하고 끝. 없으면 B로.
갈림길 B: LLM을 쓸 수 있나쓸 수 있으면 전체 에이전트 카탈로그와 대화 상태를 주고 고르게 합니다. 하나면 단일 실행, 둘 이상이면 층을 나눕니다. LLM 호출이 실패하면 설정이 required일 때는 요청이 여기서 오류로 끝나고, 아니면 C로. 못 쓰면 C로.
갈림길 C: 키워드 규칙핸드오프 예정 → 그 에이전트. 키워드 하나 → 그것. 없음 → 직전 에이전트 → 상담 구분 기본 → 절차 안내. 둘 이상 → 전부 실행.

결과는 "어떤 에이전트를 몇 층으로 돌릴지"가 담긴 계획입니다.

4. 공유 정보 준비

router.py → (family_graph 조회)

가족관계는 요청에 직접 담겨 왔으면 그것, 아니면 id로 DB 조회, 조회가 안 되면 없음. 재산 정보는 세션 값에 요청 값을 덮어 병합. 유언장 판정은 세션 값에 요청 값이 실제 점검 결과일 때만 교체. 이 셋이 이번 턴 모든 에이전트에 들어갑니다.

5. 에이전트 실행

router.py → planner.py → handoff.py → agents/*/agent.py

계획의 층을 앞에서부터 돕니다. 에이전트마다 입력을 조립하는데, 전용 상태는 handoff.py 규약대로 세션 저장 상태와 이번 요청 값을 합친 것이고, 앞 층이 있었으면 앞 층의 상태와 답변도 넣습니다. 실행 함수는 registry.py가 spec.py에서 가져온 것입니다.

갈림길: 층에 에이전트가 몇 개인가하나면 그 자리에서 호출, 둘 이상이면 스레드로 동시에.
갈림길: 에이전트가 예외를 던졌나던졌으면 그 자리만 사과 문구로 대체하고 나머지는 계속.

층이 끝나면 에이전트가 돌려준 재산 정보를 병합하고 유언장 판정이 새로 나왔으면 교체합니다. 다음 층은 이 값을 받습니다. 결과는 실행 순서대로의 에이전트별 출력과 병합된 공유 정보입니다.

6. 답변 합치기

router.py → compose.py → (llm_policy.py, LLM)
갈림길: 출력이 몇 개인가하나면 원문 그대로. 둘 이상이면 아래로.
갈림길: LLM 합성이 됐나LLM을 못 쓰거나 실패했으면 원문을 소제목 붙여 이어 붙이고 검증 통과로 표시. 합성문이 나왔으면 숫자·날짜 검증. 통과면 합성문, 불일치가 있으면 이어 붙이기로 돌아가고 검증 실패로 표시.

그 다음 router.py가 최종 응답을 조립합니다. 대표 에이전트는 마지막에 실행된 것, 답변은 위 결과, 에이전트별 원문은 별도 목록, 실행 경로와 검증 결과를 함께 담습니다.

7. 세션 저장

router.py → handoff.py → session_store.py → (Postgres면 models.py 테이블)

실행된 에이전트마다 출력에서 자기 상태를 뽑아 세션에 넣습니다. 핸드오프 신호를 낸 에이전트가 있으면 다음 턴 대상으로 기억합니다. 여럿이 냈으면 나중 것이 이깁니다. 마지막 에이전트를 직전 에이전트로 기록하고, 병합된 재산 정보와 유언장 판정을 세션에 반영합니다. 최종 응답이 "사용자 답을 기다린다"는 신호였으면 그 에이전트를 답변 대기 에이전트로 기억합니다. 최종 답변을 이력에 붙이고 저장소에 씁니다.

갈림길: 저장소 종류인메모리면 소유자 확인 후 딕셔너리에. Postgres면 행이 없으면 만들고, 소유자가 다르면 거부하고, 만료 시각을 지금 더하기 보관 기간으로 갱신해 커밋.

8. 응답 반환

router.py → main.py → 프론트

잠금을 놓고 최종 응답을 돌려줍니다. 프론트는 답변을 말풍선에, 에이전트별 원문을 카드에, 검증 실패면 확인필요 배지를, 실행 경로를 개발자 패널에 그립니다.

한 장 요약

main.py ─▶ router.py 진입 ── 세션 잠금
   │
   ├ 2. 세션 읽기 ─────────── session_store.py (인메모리 | Postgres+models.py)
   ├ 3. 누가 답할지 ────────── planner.py ← registry.py(spec.py 카탈로그, 키워드)
   │      A 답변 대기 중? → LLM에 이어가기/새 주제 질문 (실패 시 유지)
   │      B LLM 가능?     → 카탈로그 보고 고름 ← llm_policy.py
   │      C 규칙          → 핸드오프 / 키워드 / 직전 / 상담구분 / 기본
   │      둘 이상         → 필요·생산 정보로 층 나누기
   ├ 4. 공유 정보 ─────────── 가족관계 · 재산 · 유언장 판정 병합
   ├ 5. 실행 ──────────────── planner.py ← handoff.py(입력 조립) → agents/*/agent.py
   │      층마다 병렬, 실패는 그 자리만 대체
   ├ 6. 합치기 ────────────── compose.py: 1개 원문 / LLM 합성 → 숫자 검증 → 통과 | 이어붙이기
   ├ 7. 저장 ──────────────── handoff.py(상태 추출) → session_store.py
   │
   ▼
main.py ─▶ 프론트

3. 흐름 밖에서 쓰이는 것들

위 여덟 단계에 등장하지 않는 것들과, 언제 누가 쓰는지입니다.

  • session_api.py: 재로그인 직후 프론트가 한 번 부릅니다. 세션 저장소에서 사용자의 최근 세션을 찾아 돌려주고, 프론트는 그 세션 id로 2단계부터 이어갑니다.
  • 만료 정리 배치 (main.py → session_store.py): 15분마다 만료된 세션을 실제로 삭제합니다. 예전에는 조회할 때 무시만 하고 행은 영구히 남았는데, 비로그인 대화의 원문과 사망일, 재산 정보가 계속 쌓인다는 뜻이라 지우는 쪽으로 바꿨습니다. 같은 배치가 방치된 익명 가족관계도 지웁니다.
  • 저장소 교체와 조회 함수 (router.py): 기동 시 main.py가 저장소를 갈아끼울 때, 그리고 session_api.py와 정리 배치가 "지금 꽂혀 있는 저장소"를 물을 때 씁니다. 저장소 변수를 직접 가져가면 교체 전 값을 붙들기 때문에 함수를 통하게 했습니다.
  • 헬스체크 상태 (llm_policy.py → main.py): 턴 처리와 무관하게, LLM을 쓰려는데 키가 없어 규칙 폴백으로 도는 상태를 밖에서 알아채기 위한 것입니다.
  • models.py와 마이그레이션: 흐름에서는 Postgres 저장소 안에서만 쓰이지만, DB 마이그레이션 도구가 이 파일을 보고 테이블을 만듭니다. 테이블 정의의 출처는 이 파일 하나입니다.
  • 테스트 전용 장치: router.py에는 특정 에이전트만 가짜로 바꿔 끼우는 표가 있고(실제 실행에서는 비어 있음), registry.py에는 목록을 비우거나 직접 넣는 함수가, planner.py에는 각 에이전트 팀이 "내 spec이 프롬프트에 실리는가"를 검사할 때 쓰는 별칭이 있습니다. 계획과 실행 결과에는 "LLM이 실제로 쓰였나", "에이전트가 실제로 받은 입력이 뭔가"를 확인하는 디버그 필드가 있습니다.
  • 지금은 비어 있는 자리: handoff.py에는 네임스페이스 규약을 아직 안 따르는 에이전트를 임시로 넣는 집합이 있습니다. 예전에 유언장 점검 에이전트가 여기 있었고 규약으로 옮긴 뒤 비었습니다. session_store.py의 세션 잠금은 인메모리만 구현했고 Postgres는 기본값(잠그지 않음)을 씁니다.
  • __init__.py: 진입점과 저장소 교체 함수 두 개만 밖으로 노출합니다.
