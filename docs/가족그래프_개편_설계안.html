가족그래프 개편 설계안

평평한 가족 목록을 사람(노드) + 관계(엣지) 그래프로 바꾸고, 대화 대신 트리 그리기 온보딩으로 가족을 입력받는다.

확정 · 1차 구현 완료 작성 정민 · 2026-08-25 마이그레이션 b3e7d20c5f14 판정 엔진은 스텁

머지 시 주의. 이 마이그레이션은 family_members 테이블을 drop하는 파괴적 변경이다. 머지 직후 팀 전체가 git pull + alembic upgrade head를 해야 하며, 공용 Railway DB에 적용되는 순간 옛 코드의 family-graph API는 동작하지 않는다 (§9-F).

1 · 왜 바꾸나

기존 family_members는 모든 구성원이 "피상속인과 어떤 관계인지" 한 칸만 가진 평평한 리스트다. 구성원끼리의 연결이 없으니 "먼저 죽은 둘째의 아들"과 "그냥 손자"를 구별할 수 없다.

리스트로는 못 하는 것근거
대습상속 — 먼저 사망한 자녀의 자녀가 대신 상속민법 제1001조
특별대리인 필요 판정 — 미성년 상속인의 친권자가 공동상속인인지민법 제921조
상속 순위 이동 — 1순위 전원 부재 시 2순위로민법 제1000조
재혼 가정(전혼 자녀)·양자·사실혼 구분—

여기에 더해 가족 정보를 대화에서 추출하지 않고, 진입 시 사용자가 직접 입력하는 온보딩으로 바꾼다. 정확도 100%, 대화 UX 부담 제거.

2 · 결정사항 2026-08-25

① 스키마

리스트 → persons(노드) + relations(엣지) 전면 이행. GEDCOM 모델 참고. 피상속인도 명시적 노드.

② 입력 UI

폼 나열이 아니라 시각적 가족 트리 + 카드 클릭으로 추가. 피상속인을 중앙에 두어 "누구 기준 관계인가" 혼란을 없앤다.

③ 질문 흐름

민법 1000조 순위 순서대로 묻는 인터뷰 위저드(배우자 → 자녀 → 직계존속 → 형제자매). 복잡 케이스 질문은 조건부로만 펼친다.

④ 어휘

가족관계증명서·안심상속 원스톱 서식의 용어를 그대로. 증명서 보며 옮겨 적는 시나리오 지원.

⑤ 진입

초기 온보딩 + "나중에 할게요" 스킵 + 대화 중 재진입(에이전트가 협의·상속인 얘기 시 안내).

⑥ 호환 경계

에이전트가 쓰는 {"heirs": [...]}는 get_heirs_dict()가 그래프에서 파생. 에이전트 코드는 손대지 않는다.

⑦ 불완전성

혼외자·태아·연락두절은 어떤 폼도 못 받는다. "미확인" 상태를 두고, 안내문에 "가족관계증명서로 확인된 상속인 기준" 한정 문구.

3 · 스키마와 예시 데이터

persons
  id               PK
  family_graph_id  FK
  name             표시용 호칭 (실명 강제 안 함 — "첫째" 허용)
  is_decedent      피상속인 표시 (그래프당 정확히 1)
  is_alive         생존 여부
  death_date       사망일 (대습 판정: 피상속인보다 먼저인지)
  birth_date       생년월일 (선택 — 미성년 파생)
  is_minor         birth_date 없을 때의 직접 입력값
  status           confirmed | unconfirmed

relations
  id       PK
  from_id  FK persons
  to_id    FK persons
  type     parent_of | spouse_of
  attrs    JSON (법률혼 여부, 친생/양자 — 필요해질 때)

4 · 관계 라벨은 저장하지 않고 파생한다

repository.derive_heirs가 피상속인 노드에서 출발해 엣지를 따라가며 라벨을 붙인다. 에이전트는 이 결과(get_heirs_dict())만 본다.

5 · 상속인 판정 엔진 스텁만 존재

그래프는 데이터일 뿐이다. "이 그래프에서 상속인이 누구인가"를 계산하는 엔진이 있어야 값어치를 한다. 지금은 family_graph/engine.py에 v1 범위 명세 주석만 있고, 엔진이 들어오기 전까지 대습상속 입력 UI는 잠금 상태다.

v1 기능근거 조문비고
상속 순위 계산 (직계비속 → 직계존속 → 형제자매 → 4촌 방계)민법 제1000조4촌 방계는 v1 제외 가능
배우자 공동상속 / 단독상속민법 제1003조
대습상속민법 제1001조death_date로 선사망 판정
특별대리인 필요 판정민법 제921조미성년 상속인의 parent_of가 공동상속인인지
법정상속분 (배우자 1.5 : 자녀 1)민법 제1009조tax_calculator 기존 계산과 단일화 — 승원 협의

heir_navigator의 절차 데이터와 같은 철학: 모든 판정 규칙에 근거 조문 + verified 플래그. LLM은 판정에 관여하지 않는다. 결격(1004조)·상속포기 반영은 v1 제외 제안 (§9-C).

6 · 온보딩 화면

사용자는 "관계를 입력한다"가 아니라 "가족 그림을 그린다"고 느껴야 한다. 카드를 추가하는 행위 자체가 엣지 입력이 된다.

인터뷰 위저드 — 법이 따지는 순서 = 질문 순서

9 · 결정 기록과 남은 사안

결정됨 (2026-08-25, 정민)

  • A. 일정 — 그래프 개편은 지금 진행(완료). 판정 엔진만 뒤로.
  • B. 기존 family_members — 교체(마이그레이션에서 drop). 적용 시점 데이터는 팀 테스트 행뿐.
  • C. 판정 엔진 — 스텁만. 실구현 시점은 팀 결정. 엔진 전까지 대습상속 입력 UI 잠금.
  • D. 트리 UI — 자체 구현(카드+위저드, 라이브러리 불사용). 풀 그래프 시각화가 필요해지면 재검토.

남은 사안

  • E. 법정상속분 계산 단일화 — tax_calculator의 계산을 engine.py로 옮길지 (승원 협의). 판정 엔진 착수와 같은 시점 제안.
  • F. 마이그레이션 적용 시점 — family_members drop이므로 머지 직후 팀 전체 git pull + alembic upgrade head. 공용 Railway DB 적용 순간 옛 코드의 family-graph API 중단.
  • G. 판정 엔진 실구현 여부 — "상속인 자동 판정"은 기존 요구사항에 없던 신규 기능이라 제품 범위 채택 여부를 팀이 결정.
