# 가족 자산 준비 AI 에이전트 — 개발/배포 파이프라인 계획

작성일: 2026-08-14

이 문서는 기획서(5장 "개발 구조 및 방법")에 정의된 아키텍처와 개발 원칙("뼈대 먼저", "항상 실행 가능", "계약 먼저", "작게 자주 합치기")을 실제 GitHub 기반 개발·배포 파이프라인으로 옮기기 위한 계획입니다. 프론트엔드(React), 오케스트레이터/에이전트 백엔드(FastAPI + LangGraph), DB, CI/CD를 모두 포함합니다.

---

## 1. 저장소 구조

4명이 4개 모듈(오케스트레이터+가족관계엔진은 지원님, 3개 에이전트는 각 팀원)을 나눠 맡는 구조이므로, 저장소를 잘게 쪼개기보다 **하나의 모노레포**로 시작하는 것을 권합니다. 레포를 나누면 스키마(AgentInput/AgentOutput)가 바뀔 때마다 여러 레포를 동시에 맞춰야 해서 "계약은 코드보다 먼저" 원칙과 충돌하기 쉽습니다.

```
repo-root/
├── apps/
│   ├── web/                # React 프론트엔드 (모바일 웹)
│   └── api/                # FastAPI + LangGraph 오케스트레이터
│       ├── orchestrator/
│       ├── agents/
│       │   ├── heir_navigator/       # 상속인 절차 내비게이터 (정민)
│       │   ├── decedent_estate/      # 피상속인 유언장·자산정리 (정호)
│       │   └── tax_calculator/       # 상속세 계산·설계 (승원)
│       ├── family_graph/   # 가족관계 그래프 엔진 (지원)
│       └── schemas/        # AgentInput/AgentOutput 등 공통 계약
├── infra/
│   ├── docker-compose.yml  # 로컬 개발용 (api + postgres)
│   └── Dockerfile.api
├── .github/
│   └── workflows/
├── docs/
└── README.md
```

`schemas/`를 별도 디렉토리로 분리해두면 2단계(스키마 확정) 산출물이 코드베이스 안에서 곧바로 "단일 진실 공급원(source of truth)"이 되고, 3~4단계에서 에이전트를 교체할 때 계약 변경 여부를 diff로 바로 확인할 수 있습니다.

## 2. 브랜치 전략

인원이 적고 개발 기간이 짧은 해커톤 성격이므로 GitFlow 같은 무거운 전략보다 단순화된 트렁크 기반 전략을 권합니다.

- `main` — 항상 배포 가능한 상태 (원칙 2 "항상 실행 가능"과 직결). Vercel/Railway 프로덕션 환경에 자동 배포.
- `develop` — 팀 통합 브랜치. "작게 자주 합치기" 원칙에 따라 3~4일마다가 아니라 매일 PR 머지를 권장. 여기에 미리보기(Preview) 배포 연결.
- `feature/agent-heir`, `feature/agent-decedent`, `feature/agent-tax`, `feature/orchestrator` 등 담당자별 작업 브랜치.

PR은 `feature/* → develop`으로 올리고, 최소 1인 리뷰 후 머지. `develop → main`은 6단계(다듬기) 진입 시점이나 각 마일스톤에서 지원님이 직접 머지하는 방식을 권합니다.

## 3. 환경(Environment) 구성

세 단계로 나눕니다.

| 환경 | 용도 | 프론트 | 백엔드 | DB |
| --- | --- | --- | --- | --- |
| local | 개인 개발 | `npm run dev` | `uvicorn --reload` | Docker Postgres |
| preview | PR/develop 검증 | Vercel Preview (PR마다 자동 생성) | Render/Railway PR 환경 또는 develop 브랜치 상시 배포 | 별도 스테이징 DB (또는 Railway free tier) |
| production | 실제 제출·데모용 | Vercel Production | Railway/Render Production | Production Postgres |

Vercel은 PR을 열면 자동으로 프리뷰 URL을 만들어주므로 프론트는 별도 설정 없이 이 구조를 얻을 수 있습니다. 백엔드(Railway/Render)는 PR 프리뷰가 유료 플랜이거나 제한적인 경우가 많아, 현실적으로는 `develop` 브랜치를 상시 스테이징으로 띄워두고 팀원들이 프론트 프리뷰에서 이 스테이징 API를 바라보게 하는 방식이 간단합니다.

## 4. DB 선택과 마이그레이션

기획서에 DB가 명시되어 있지 않아 다음을 가정합니다: **PostgreSQL**, **Railway**의 관리형 Postgres 사용 (선정 이유는 아래 4-1 참고. Vercel은 프론트 전용이므로 DB는 백엔드와 같은 플랫폼에 두는 것이 네트워크 지연·설정 면에서 유리).

### 4-1. Railway vs Render — Railway 추천

| 비교 항목 | Railway | Render |
| --- | --- | --- |
| 요금 방식 | 사용량 기반. Hobby 플랜은 월 $5을 내면 그만큼 크레딧으로 소진, 안 쓰면 그만큼 안 나감 | 워크스페이스 요금(무료/Pro $25 등) + 서비스별 컴퓨트 요금(Starter $7 등) 이중 구조 |
| 무료 티어 백엔드 | 무료 플랜도 있으나 크레딧이 적어 실질적으로는 Hobby($5~)로 시작하는 경우가 많음 | Free 웹서비스 제공하지만 **15분간 요청이 없으면 슬립(spin down)** — 다시 깨어날 때 첫 요청이 수십 초 지연됨 |
| 데모/발표 적합성 | 상시 켜져 있어 심사 중 응답 지연 걱정이 적음 | 데모 도중 오랜만에 요청하면 첫 응답이 느려질 수 있어 해커톤 발표에는 리스크 |
| PR/프리뷰 환경 | 유료 플랜(Hobby 이상)에서 지원 | Hobby는 단일 서비스 프리뷰만, 풀스택 프리뷰는 Pro($25~) 이상 |
| Postgres | 서비스 하나로 같이 관리, 크레딧에 포함 | 무료 Postgres는 **30일 후 만료** — 별도로 유료 전환(월 $6~) 필요 |

**추천: Railway.** 해커톤처럼 짧은 기간에 데모·심사가 걸려 있는 프로젝트에서는 Render 무료 플랜의 "15분 슬립 → 재요청 시 지연" 특성이 가장 큰 리스크입니다. Railway는 사용량 기반이라 트래픽이 적은 개발 기간에는 월 $5 안에서 대부분 해결되고, DB까지 한 플랫폼에서 같이 운영할 수 있어 설정도 단순합니다. 예산이 아주 빠듯하다면 Render Free로 시작하되 발표·심사 직전에는 최소 Starter($7)로 잠깐 올려 슬립을 끄는 절충안도 가능합니다.

- ORM: SQLAlchemy + Alembic (FastAPI와 궁합이 좋고 마이그레이션 이력 관리 가능)
- 로컬 개발은 `docker-compose`로 Postgres 컨테이너를 띄워 프로덕션과 동일한 엔진 사용 (SQLite로 로컬만 다르게 가면 나중에 타입 차이로 마이그레이션 이슈가 남)
- 세션 상태(session_state), 가족관계 그래프, 조회결과 캐처 이미지 메타데이터 등 스키마가 2단계에서 확정되는 대로 첫 Alembic 마이그레이션 작성

민감정보(가족관계, 재산 정보)를 다루는 서비스이므로, 실제 배포 DB는 최소한 저장 시 암호화(at-rest encryption, 관리형 DB는 기본 제공)와 접근 IP 제한 정도는 초기부터 켜두는 것을 권합니다.

### 4-2. OCR 연동 (MVP 포함 확정)

조회결과 캐처 이미지에서 텍스트를 뽑아내는 용도로는, **별도 OCR API를 새로 붙이기 전에 이미 사용 중인 Claude API의 비전(이미지 인식) 기능을 1차로 활용하는 것**을 권합니다.

- 사용자가 업로드한 스크린샷을 그대로 Claude API에 이미지로 전달하고, "은행명 / 잔액 확인 여부 / 계좌 존재 여부"처럼 원하는 구조로 뽑아달라고 프롬프트로 요청하면 됩니다.
- 장점: 별도 벤더 계약·요금제·API 키 관리가 필요 없고, "결과 해석"이라는 서비스의 핵심 개입 지점과 텍스트 추출을 한 번의 LLM 호출로 합칠 수 있어 오케스트레이터 구조도 단순해집니다.
- 다만 화질이 나쁘거나 표가 복잡한 스크린샷에서는 전용 OCR보다 정확도가 떨어질 수 있습니다. 4단계(에이전트 실제 로직 교체) 진행하면서 실제 캡처 이미지 샘플로 정확도를 확인해보고, 부족하면 네이버 클로바(CLOVA) OCR 등 전용 OCR을 폴백으로 추가하는 2단계 접근을 권합니다. (클로바 OCR은 네이버클라우드플랫폼 콘솔에서 신청·견적을 받아야 정확한 단가를 알 수 있어, 필요 시점에 콘솔에서 직접 확인 필요)
- 이렇게 하면 MVP 단계에서는 추가 비용·연동 공수 없이 "가능하다면 할 것"으로 표시된 OCR을 실질적으로 포함시킬 수 있습니다.

## 5. CI (GitHub Actions) — PR마다 자동 검증

`.github/workflows/ci.yml` 하나로 프론트/백엔드를 경로 기반으로 분기합니다.

- **frontend job**: `apps/web/**` 변경 시 트리거 → `npm ci` → `lint` → `build` (배포 전에 빌드 깨짐을 미리 잡음)
- **backend job**: `apps/api/**` 변경 시 트리거 → `pip install` → `ruff`/`black --check` → `pytest` (에이전트별 unit test는 각자 담당 폴더에 최소 1개씩부터 시작 — "항상 실행 가능" 원칙을 코드로 강제)
- **schema check job**: `schemas/` 변경 시 다른 팀원에게 자동 코멘트/멘션 (계약 변경은 영향 범위가 크므로)

PR이 CI를 통과해야만 머지 가능하도록 브랜치 보호 규칙(Branch protection rule)을 `develop`, `main`에 설정합니다.

## 6. CD — 배포 자동화

**프론트엔드 (Vercel)**
Vercel의 GitHub 연동을 그대로 사용하는 것이 가장 간단합니다. GitHub Actions로 별도 배포 스텝을 만들 필요 없이, Vercel 프로젝트를 이 레포의 `apps/web`에 연결하면 push마다 자동 배포됩니다 (Root Directory를 `apps/web`으로 지정).

**백엔드 (Railway — 선정 이유는 4-1 참고)**
GitHub 연동 시 push 기반 자동 배포를 지원합니다. `apps/api`를 Root Directory로 지정하고 `infra/Dockerfile.api`로 빌드하도록 설정하면 별도 Actions 워크플로 없이도 배포됩니다. 다만 배포 전에 CI(테스트)를 반드시 통과시키고 싶다면 GitHub Actions에서 `workflow_dispatch`를 사용해 CI 통과 후에만 배포되도록 묶는 것을 권합니다.

**환경변수/시크릿 관리**
Claude API 키, DB 연결 문자열 등은 절대 레포에 커밋하지 않고 각 플랫폼(Vercel/Railway)의 환경변수 설정과 GitHub Actions Secrets에 등록합니다. `.env.example`만 레포에 포함해 어떤 변수가 필요한지 팀원들이 알 수 있게 합니다.

## 7. 로컬 개발 환경 통일

`infra/docker-compose.yml`로 API + Postgres를 한 번에 띄워 팀원 간 "내 컴퓨터에서는 되는데" 문제를 줄입니다.

```yaml
services:
  api:
    build: ./apps/api
    ports: ["8000:8000"]
    env_file: .env
    depends_on: [db]
  db:
    image: postgres:16
    environment:
      POSTGRES_PASSWORD: devpass
    ports: ["5432:5432"]
    volumes: ["pgdata:/var/lib/postgresql/data"]
volumes:
  pgdata:
```

프론트는 Docker 없이 `npm run dev`로 충분합니다 (Vercel 배포 환경과 로컬 Node 환경 차이가 크지 않음).

## 8. 기획서의 6단계 개발 순서에 맞춘 파이프라인 작업 매핑

| 개발 단계 | 이번 문서 기준으로 병행할 파이프라인 작업 |
| --- | --- |
| 1단계 (스키마/계약 확정) | 레포 생성, `schemas/` 디렉토리 확정, 브랜치 보호 규칙 설정 |
| 2단계 (오케스트레이터 최소 뼈대, "배포 파이프라인부터 구축") | GitHub Actions CI 워크플로 작성, Vercel·Railway 연동, `docker-compose` 로컬 환경, 첫 mock 배포로 파이프라인 자체를 검증 |
| 3단계 (가족관계 그래프 엔진) | Alembic 첫 마이그레이션, DB 스테이징 환경 연결 |
| 4단계 (에이전트 3개 실제 로직 교체) | `feature/agent-*` 브랜치별 PR·리뷰 루틴 가동, 에이전트별 unit test 추가 |
| 5단계 (시나리오 A/B 리허설) | `develop` 브랜치 상시 배포본으로 엔드투엔드 리허설, 필요 시 OCR(캐처 이미지 텍스트 추출) 연동 환경변수 정리 |
| 6단계 (다듬기 + 제출물 정리) | `main` 프로덕션 배포 고정, README/제출용 문서 정리, 시크릿 최종 점검 |

## 9. 지금 바로 할 수 있는 체크리스트

1. GitHub 조직/레포 생성, 팀원 4명 초대 및 권한 설정
2. 위 모노레포 구조로 초기 커밋 (빈 폴더 + `.gitkeep`도 무방)
3. `develop`, `main` 브랜치 생성 및 보호 규칙 설정 (PR 필수, CI 통과 필수)
4. Vercel 프로젝트 생성 → `apps/web` 연결
5. Railway 프로젝트 생성 → `apps/api` 연결 + Postgres 애드온 추가
6. `.env.example` 작성 (CLAUDE_API_KEY, DATABASE_URL 등)
7. `.github/workflows/ci.yml` 작성 (lint + test, 프론트/백엔드 분기)
8. mock 오케스트레이터 + mock 에이전트 3개로 "뼈대"를 만들어 위 파이프라인 전체(로컬 → PR → CI → develop 배포 → main 배포)를 한 번 끝까지 실행해보고 검증

이 체크리스트가 곧 2단계("오케스트레이터 최소 뼈대... 배포 파이프라인부터 구축")의 실행 계획이 됩니다. 파이프라인이 한 번 끝까지 도는 것을 확인한 뒤 3~4단계로 넘어가면, 이후에는 로직만 갈아 끼우면 되므로 원칙 1("뼈대 먼저, 살은 나중에")이 자연스럽게 지켜집니다.

## 10. 개인정보 보관 기간·삭제 정책 (초안)

가족관계·재산 정보처럼 민감한 데이터를 다루므로, 실제 서비스로 확장할 때는 개인정보보호법에 따른 개인정보처리방침 게시와 별도 법률 검토가 필요합니다 (이 문서는 그 대체가 아닙니다). 다만 해커톤 MVP 단계에서 개발 원칙에 바로 반영할 수 있는 기본값은 아래처럼 정해두는 것을 권합니다.

### 아직 정해지지 않아 팀 논의가 필요한 항목

- 개인정보 보관 기간의 정확한 숫자(30일, 1년 등)는 팀 내부 논의로 최종 확정 필요 — 위 표는 출발점입니다
- OCR을 Claude 비전으로 우선 처리하기로 했으나, 실제 캡처 이미지로 정확도 테스트 후 클로바 OCR 등 폴백 도입 여부는 4단계에서 재확인 필요
- 실제 서비스화 단계에서는 개인정보처리방침 게시, 위탁처리 동의 등 법률 검토가 별도로 필요
