# 자산정리·은퇴설계 → 상속세 연동

## 이번 변경 범위

- `payload.financial_profile`을 읽고 상속세 상태 안에 확인 전 자료와 후보 합계를 저장한다.
- 계산 엔진(`calculator.py`), 공용 스키마, 라우터, 팀원 에이전트는 변경하지 않는다.
- 공유 자료의 소유자가 이번 피상속인인지, 사망일 기준 자료인지, 누락이 없는지 먼저 확인한다.
- 후보를 질문에 보여주고 사용자가 `네` 또는 수정 금액을 입력한 뒤 계산에 사용한다.
- `모름`, `알 수 없어요`, `정보 없어요`는 0원이 아니다. 결과를 보류하며 이전 세액도 반환하지 않는다.

## 팀원 문의 1~4에 대한 처리

### 1. 금융재산

`extra.asset_organizer.assets`의 예금·적금·주식·펀드는 금융재산 **후보**로 합산한다.
이는 확정 공제 판정이 아니다. 질문에서 최대주주 등 보유주식·미신고 타인명의
금융재산 등 제외 가능성을 안내하고 사용자 확인을 받는다.

`기타`·미분류 자산은 전체 재산 후보에는 남기되, 금융재산 후보 총액을 확정하지 않는다.
금액 누락·음수·잘못된 타입·미확인 표시가 있는 목록은 유효한 항목만 골라 전체액인 것처럼
합산하지 않는다. 빈 목록의 0원 역시 자료 범위 확인과 금액 확인을 거쳐야 한다.

항목별 목록이 있으면 해당 목록을 사용한다. 그 목록이 불완전하더라도 flat 집계로
우회하지 않는다. 항목별 목록이 없으면 부동산·금융·기타 3개 합계가 모두 유효할 때만
전체 재산 후보를 만든다. 세 항목은 상호 중복이 없어야 한다.

shared `financial_assets=0`은 기존 브릿지의 임시값일 수 있으므로 그 자체로
공제대상 금융재산 0원을 확정하지 않는다. 일반 자산 총액과 세법상 공제 대상액은 구별한다.
팀원이 금융자산을 `other_assets`에서 옮기면 양쪽 합계도 같이 갱신해야 중복되지 않는다.

### 2. 금융채무

`Liability.type`은 변경하지 않는다. 대출·카드론·전세자금대출이라는 이름만으로
금융기관 채무라고 판단하지 않고, 금융채무 금액을 직접 확인한다.

향후 항목별 원본에 선택적으로 `creditor_category`를 제공한다면 다음 두 값만 후보
분류에 사용한다: `financial_institution`, `non_financial`.
이는 세금 담당 내부 브릿지가 지원하는 선택 정보이며 **공용 계약에 필수 추가한 필드가 아니다**.
모든 채무 항목에 구분과 유효한 잔액이 있어야 금융채무 후보를 만든다.
구분이 없거나 다른 값이면 질문 경로를 유지한다. 실제 채무 인정·증빙 심사를 대신하지 않는다.

### 3. 간주상속재산

보험금·신탁재산·퇴직급여를 각각 질문한다. 보험 가입금액을 사망보험금으로 변환하지 않는다.
3개 모두 확인된 0원이면 간주상속재산 0원을 저장한다.

양수가 있으면 보험료 부담자·신탁 권리 내용·유족연금 등 제외 항목과 기존 재산 중복 여부를
안내한다. 전액 과세 포함 및 중복 없음이 신고자료나 세무 전문가를 통해 확인됐다고 답한
경우에만 합산한다. 확인 전에는 `last_result=None`이며, `아니요`는 `needs_review`로 반환한다.
입력액 수정은 `다시 입력`으로 가능하다.

이 MVP는 보험료 부담비율별 과세액, 신탁 권리 평가, 퇴직급여의 법적 제외액을
자동 판정하지 않는다. 일부만 과세되는 복합 사례는 확인된 계산 입력을 제공해야 한다.
보험금 등이 양수이면 기존 자산 후보만으로 금융재산 공제를 확정하지 않고 별도로 묻는다.

### 4. 연결 경로와 우선순위

공유 경로는 `payload.financial_profile`을 사용한다. 별도 엔드포인트나 router 수정은 없다.
기존 `context.tax_input`은 **사용자 또는 확인된 세금 입력을 명시적으로 전달하는 경로**로 유지한다.
명시적 입력은 공유 후보보다 우선하며 같은 턴의 채팅으로 다시 덮어쓰지 않는다.
`None`을 명시적으로 보내면 해당 항목을 미확인으로 되돌린다.

기존 `to_tax_input()`에서 미확인 0원·보험금 합계를 자동 생성하여 `context.tax_input`으로
보내는 동작은 병행하지 말 것. 같은 자료는 shared profile로 보내고 이 모듈에서 후보로 처리한다.
이미 전달한 임시 0원은 공유 스키마의 None 병합으로 삭제되지 않으므로 과거 테스트 세션과
새 연동 확인용 세션을 구분하는 것이 좋다.

## 상태와 갱신

`data.tax_calculator`에 다음 상태를 기존 values/confirmed_fields와 함께 저장한다.

- `profile_snapshot`: 상속세 관련 공유 자료 스냅샷(은퇴 나이 등은 제외)
- `profile_candidates`: 확인 전 합계
- `profile_scope_confirmed`: 피상속인·시점·범위 확인
- `profile_sources`: 사용자 / 명시적 입력 / 확인받은 공유 후보의 출처
- `profile_reconfirm`: 변경된 후보와 기존 직접 입력이 충돌하는 항목
- `deemed_items`: 항목별 보험금·신탁·퇴직급여

공유 자료 변경 시 이전 결과 및 공유 후보 출처의 확정값을 무효화한다.
직접 입력한 금액은 지우거나 몰래 덮어쓰지 않고 충돌하면 다시 확인한다.
이전 항목별 간주상속재산 답변도 재확인한다. 이전 질문의 답을 새 스냅샷에 자동 적용하지 않는다.
메모리 세션을 사용하는 실제 오케스트레이터 왕복 테스트로 네임스페이스 보존을 확인한다.

## 결과와 한계

계산 결과의 경고는 `reply`뿐 아니라 `last_result.warnings`에도 넣는다.
0원 결과에도 납세·신고 의무가 없다는 확정 판단이 아님을 표시한다.
과세 자격·증빙·재산 평가를 자동 확인하는 기능이나 미확인값을 0원으로 가정하는
부분 시뮬레이션은 제공하지 않는다. 조건이 미확인되면 질문/검토 경로에 머문다.
