# 요건 판정기(규칙 기반) 알려진 한계

작성 기준: `date_parser.py` / `requirement_checker.py` 구현 및 샘플 A/B/C 테스트 과정에서
발견된 정규식·규칙 기반 v1 엔진의 한계 목록. 새로 발견되는 항목은 여기 계속 추가할 것.

분류 기준:
- **LLM 추출 단계에서 해결 예정**: 빌드 순서 4단계(`CLAUDE.md`)에서 LLM이 텍스트 의미를 이해해
  값을 추출하게 되면 자연히 해결되는, "문맥 이해가 필요한" 유형의 한계.
- **구조적 한계**: LLM 추출로 바꿔도 원천적으로 해결되지 않거나, 텍스트만으로는 판별 자체가
  불가능한 유형의 한계 (예: 물리적 특성, 설계상 의도된 제약).

---

## 1. 성명 (`extract_name`)

### 1-1. 문장 속에 묻힌 성명
예: `"서울 강남구 거주 김영수"`, `"장남 김철수에게 물려주며, 이는 김영수의 뜻이다"`

라벨(`유언자`/`성명`/`이름`), 도장 표시(`(인)`/`(印)`), 줄 끝 단독 표기 중 어디에도 해당하지
않고 문장 중간에 이름만 섞여 있으면 인식하지 못하고 `absent`로 판정된다.

- **분류: LLM 추출 단계에서 해결 예정**
- 참고: 샘플 C(`서울 강남구 거주 김영수`)에서 실제로 재현됨. `test_decedent_requirement_checker.py`
  에는 아직 이 케이스에 대한 통과 조건을 넣지 않음(현재는 `absent`가 "정직한" 현재 동작).

### 1-2. 알리아스(아호) 라벨도 콜론 필수
`_NAME_ALIAS_RE`는 `"아호: OO"` / `"호: OO"`처럼 콜론이 있어야만 인식한다. 반면 이름 라벨
(`_NAME_LABEL_RE`)은 이번에 콜론을 선택 사항으로 완화했기 때문에, 같은 문서 안에서도
"이름 라벨은 콜론 없이 인식되는데 아호 라벨은 콜론이 없으면 놓친다"는 비일관이 생긴다.

- **분류: LLM 추출 단계에서 해결 예정** (규칙 일관화만으로도 완화 가능하지만, "이 표기가 본명인지
  아호인지" 자체가 의미 판단이라 근본 해결은 LLM 쪽)

### 1-3. 줄 끝 단독 이름 판별의 형식 의존성
`_NAME_STANDALONE_LINE_RE`는 해당 줄이 정확히 2~4자 한글로만 이루어져야 매칭된다.
`"김 영 수"`(띄어쓰기 서명), `"홍길동 올림"`, `"홍길동(자필)"`처럼 부가 문구가 붙으면 놓친다.
블록리스트(`유언장`/`유언`/`증인`/`서명`/`이상`/`끝`)도 하드코딩된 소수 단어라, 다른 문서
구조어(`"각서"`, `"확인서"`, `"별지"` 등)가 등장하면 이름으로 오인될 수 있다.

- **분류: 구조적 한계** (형식이 조금만 벗어나도 깨지는 것은 정규식 접근 자체의 근본적 제약이며,
  블록리스트를 아무리 늘려도 새로운 반례가 계속 나올 수 있음 — 다만 LLM 추출로 상당 부분 완화는 됨)

## 2. 주소 (`extract_address`)

### 2-1. 유언자 주소가 재산 관련 문구와 같은 줄에 있는 경우
`_ADDRESS_PROPERTY_CONTEXT_RE`(소유/부동산/명의로/아파트를/상속한다/증여한다 등)가 걸린 줄은
주소 후보에서 통째로 제외한다. 그런데 만약 유언자 본인 주소가 우연히 그 줄과 같은 문장에
섞여 있으면(예: `"서울 강남구에 사는 나는 내 아파트를 장남에게 상속한다"`) 진짜 주소까지
같이 제외되어 `absent`로 오판될 수 있다.

- **분류: LLM 추출 단계에서 해결 예정** ("이 주소가 누구의 주소인가"는 문맥 이해가 필요한 판단)

### 2-2. 재산 문맥 키워드가 조사(助詞) 변형에 취약
`_ADDRESS_PROPERTY_CONTEXT_RE`는 `"아파트를"`, `"건물을"`처럼 정확한 문자열만 잡는다.
`"아파트는"`, `"건물이"`, `"내가 갖고 있는 아파트"`, `"물려주고자 한다"`처럼 조사·어미가
달라지면 재산 문맥으로 인식하지 못해 부동산 주소가 다시 유언자 주소로 오인될 수 있다
(원래 있던 버그의 변형).

- **분류: 구조적 한계** (정규식은 문자열 매칭이라 한국어 교착어 특성상 조사 변화를 전부
  커버하기 어려움 — LLM은 이 문제를 상당히 줄여주지만, 규칙만으로 완전히 막기는 어려움)

### 2-3. 라벨 없는 배경 서술이 주소로 오인될 가능성
`"주소"`/`"거주"` 같은 라벨이 없어도 시/구 패턴이 감지되면 `city_district_only`로 판정한다.
`"나는 서울 강남구에서 나고 자랐다"`처럼 현재 주소가 아니라 배경 설명인 문장도 같은 방식으로
잡힐 수 있다.

- **분류: LLM 추출 단계에서 해결 예정**

### 2-4. 봉투 기재 여부는 본문 텍스트로 판별 불가
자필증서 유언은 주소를 유언장 본문이 아니라 봉투에 적어도 유효로 본 판례(97다38510)가
있다. 그런데 우리가 분석 대상으로 받는 텍스트는 유언장 본문뿐이라, 봉투에 뭐라고
적혀 있는지는 텍스트만으로는 원천적으로 알 수 없다.

- **분류: 구조적 한계 (단, 사용자 확인 질문으로 해결됨)** — `rules/requirements.json`의
  `address.followup`으로 전환해, 주소가 🔴로 판정된 경우에만 "주소가 봉투에 적혀
  있나요?"를 사용자에게 직접 확인한다. LLM 추출로도 봉투 내용까지는 알 수 없으므로
  4단계(LLM 추출 연결)로도 해결되지 않는 유형 — 텍스트 기반 파이프라인의 원천적 제약이라
  사용자 확인이 유일한 해법.

### 2-5. 지번(번지) 정확성 검증은 서비스 범위 밖
"지번이 실제와 근소하게 다른 경우"를 유효로 본 판례가 있다는 아이디어가 있었지만
(a) 이를 뒷받침할 판례를 아직 확보하지 못했고, (b) 설령 판례가 있어도 유언장에 적힌
지번이 실제 등기부상 지번과 "근소하게 다른지"를 판단하려면 외부 주소 데이터베이스와의
대조가 필요한데, 이는 규칙 기반이든 LLM 기반이든 이 서비스의 텍스트 분석 범위를 벗어난다.
그래서 `envelope_or_minor_discrepancy` 조건에서 이 부분은 아예 제외했다.

- **분류: 구조적 한계** (텍스트 분석만으로는 절대 해결 안 됨 — 실제 주소 대조 기능을
  별도로 붙이지 않는 한 LLM 추출 단계로 넘어가도 그대로 남는 한계)

## 3. 연월일 (`date_parser.py`)

### 3-1. 말로 특정하는 표현의 키워드 목록이 고정
`_VERBAL_DATE_RE`는 `칠순/팔순/구순/백수/환갑/회갑/고희/미수/백일/돌` + `(잔치/기념일)` + `에`
조합만 인식한다. `"생신"`, `"생일"`, `"결혼기념일"`, `"제사일"`, `"설날"`, `"추석"` 등 다른
기념일 표현은 아예 인식되지 않아 — 다른 날짜 표기도 없다면 `verbal_specified`가 아니라
`absent`로 떨어진다.

- **분류: LLM 추출 단계에서 해결 예정** (키워드 목록을 계속 늘리는 임시방편보다, "날짜를
  특정 가능한 사건으로 표현했는가"는 LLM이 판단하는 게 근본적으로 맞음)

### 3-2. 한글 숫자 변환은 "만"(10,000) 단위 미지원
`_sino_korean_to_int`는 십/백/천 단위까지만 처리한다. 서기 연도가 사실상 항상 네 자리라
실무상 문제될 일은 거의 없지만, 만 단위가 포함된 표기(예: `"일만이십육년"`)가 들어오면
잘못 변환되거나 매칭에 실패한다.

- **분류: 구조적 한계** (범위를 의도적으로 좁힌 설계 — 발생 가능성이 낮아 우선순위 낮음)

### 3-3. 순수 숫자 연속 표기(예: `"20260503"`) 미지원
구분자(년/월/일, 점, 하이픈) 없이 8자리 숫자만 붙어 있는 형식은 인식하지 못한다.

- **분류: 구조적 한계** (별도 포맷 하나를 더 추가하는 문제이므로 규칙으로도 해결 가능하지만,
  현재 v1 범위에는 없음 — 필요 시 규칙 추가로 해결 가능한 항목이라 "LLM 없이도" 고칠 수 있음)

### 3-4. 날짜 복수 혼재 판정이 문맥을 구분하지 못함
본문에 작성일과 무관한 날짜(예: 취득일·과거 사건 날짜 등)가 함께 언급되면, 실제로는
작성일이 하나뿐이어도 `multiple_dates_mixed`로 오판될 수 있다. 어떤 날짜가 "유언장
작성일"인지 규칙만으로는 구분하지 못한다.

- **분류: LLM 추출 단계에서 해결 예정**

## 4. 간인 (`detect_interseal`)

### 4-1. 페이지 표기 문구가 없으면 여러 장이어도 감지 불가
`(1/2)`, `"N페이지"`, `"총 N장"` 같은 명시적 표기가 텍스트에 없으면 실제로 여러 장짜리
문서여도 `single_page`로 판정된다.

- **분류: 구조적 한계** (원본 스캔/이미지 정보 없이 텍스트만으로는 물리적 장수를 알 수 없음 —
  LLM으로도 텍스트만 가지고는 해결 안 됨. OCR/이미지 메타데이터 결합이 필요)

### 4-2. 간인이 실제로 찍혔는지는 텍스트로 원천 판별 불가
간인은 각 장 사이 도장이 겹쳐 찍혔는지를 보는 것이라 텍스트만으로는 애초에 판별 대상이
아니다 (요건 자체도 법정 요건이 아니라서 참고 문구로만 처리 중).

- **분류: 구조적 한계**

## 5. 기타

### 5-1. 전문 자서 / 날인은 설계상 항상 사용자 확인 필요
텍스트만으로 손글씨 여부·도장/지장 여부를 판별하는 것은 원천적으로 불가능해서
`user_confirm` 방식으로 설계되어 있다 (한계라기보다 의도된 제약). 다만 사용자가 답변하지
않으면 `PENDING` 상태로 남는데, 이 질문을 언제·어떤 순서로 사용자에게 보여줄지는
`요건판정_문구_스펙_v1.md` 6절에 "미결"로 남아 있다.

- **분류: 구조적 한계** (텍스트 기반 파이프라인의 원천적 제약)

### 5-2. 오탐 방지 규칙(재산 문맥 제외 등)이 새 반례를 계속 낳을 가능성
2-1, 2-2에서 보듯 "이 줄을 제외한다"는 식의 블록리스트/키워드 기반 규칙은 새로운 문장
패턴이 나올 때마다 반례가 나올 수 있는 구조다. 규칙을 계속 추가하는 것보다, 일정 시점
이후에는 LLM 추출로 전환하는 것이 유지보수 측면에서 더 안정적이다.

- **분류: 구조적 한계** (정규식 기반 접근의 근본적 확장성 한계)
