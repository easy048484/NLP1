### ⚠️ 평면 폴백 우선순위 — 지시와 반대로 구현 (리뷰에서 짚일 지점)

지시는 "네임스페이스 우선"이었으나 **평면 키 우선**으로 구현했다.

네임스페이스는 *지난 턴 저장 상태*, 평면 키는 *이번 턴 사용자 입력*이다.
지난 턴 값이 이기면 사용자가 답을 정정해 다시 보냈을 때 반영되지 않는다.

실제 병합은 **2단**으로 일어난다:

```
1단 handoff.build_agent_context : {**stored_context, **namespaced_override}
2단 state.load_state            : {**state, **flat_overrides}
```

두 계층 모두 *"저장된 값을 베이스로, 이번 턴 입력이 덮어쓴다"* 는 같은 방향이다.
`handoff` 의 명시적 원칙("사용자가 이번 턴에 명시적으로 답한 값이 우선")과 일치.

검증 테스트: `test_decedent_state.py::test_flat_key_this_turn_wins_over_stored_namespace`
(관련 3개 더: `test_load_state_falls_back_to_flat_keys`,
`test_broken_flat_value_keeps_namespace_state`, `test_load_state_from_namespace`)

→ PR #15 본문에 이 근거를 명시했고, 그대로 승인·머지됐다(평면 키 우선 확정).

### 동작 확인

오케스트레이터 2턴 대화로 검증:
```
1턴: 유언장 + 자서 답변                  → 날인 PENDING
2턴: 날인 답변만 (will_type·자서 재전송 X) → 자서 GREEN, 날인 GREEN
세션 저장 내용에 원문 포함 여부: False
```

### 6-7. ✅ 테스트를 실제 LLM 호출로부터 격리 (2026-08-25)

실전 검증 중 21개 테스트가 mock 없이 실제 Anthropic API를 호출하고
있었음이 드러났다(스위트 5.98초 → 27초). CI에 키가 주입되면 매 실행마다
유료 호출 21회 이상 + Anthropic 가용성에 CI 안정성이 종속되는 문제였다.

**근본 원인 — "conftest.py가 dotenv를 안 읽으니 안전하다"는 전제가 실제로는
깨져 있었다.** `main.py` 최상단이 import 시점에 곧바로
`load_dotenv(repo_root/".env")`를 실행하는 모듈 레벨 부작용이 있는데,
`test_health.py`가 `from main import app`을 하기 때문에 pytest가 테스트를
**수집만 해도(실행 전에!)** `main.py`가 import되며 `ANTHROPIC_API_KEY`가
`os.environ` 전체에 새어 들어갔다. `conftest.py`가 dotenv를 안 읽는다는
사실 자체는 맞았지만, 그것과 무관한 경로로 같은 결과(키 유입)가 일어나고
있었다.

**판단**: `main.py`는 공용 진입점이라 이번 PR에서 건드리지 않았다 —
프로덕션 런타임에서는 이 로딩이 정확히 의도된 동작이고, 문제는 어디까지나
"테스트 프로세스에도 같은 부작용이 전이된다"는 테스트 격리 문제이므로
테스트 쪽에서 방어하는 게 맞다고 판단했다.

**해결**: `tests/conftest.py`에 함수 스코프 `autouse` fixture를 추가해 매
테스트 시작 전에 `ANTHROPIC_API_KEY`를 지운다(`monkeypatch.delenv`). 굳이
`llm_client._client()` 자체를 몽키패치하지 않고 환경변수 레벨에서 막은
이유: `test_decedent_llm_client.py`의 파싱 회귀 테스트들은 각 테스트 안에서
`monkeypatch.setenv`로 키를 다시 채우고 `anthropic.Anthropic`을 가짜로
바꿔치기해 `_client()`가 정상 동작하는 것 자체를 검증한다 — `_client()`를
통째로 무력화하면 이 테스트들이 깨진다. 환경변수만 지우면 같은
`monkeypatch` 인스턴스를 테스트 함수가 이어받아 쓰므로 두 변경(fixture의
delenv, 테스트 본문의 setenv)이 자연스럽게 합성된다.

**실호출 opt-in 경로**: `@pytest.mark.live`로 표시한 테스트는 이 자동 격리를
건너뛴다. 기본 실행(`pytest -q`)에서는 `pytest_collection_modifyitems`가
live 테스트를 deselect(스킵이 아니라 목록에서 완전히 제외)한다 —
`pytest -q --live`로 명시해야만 실행되며, 그때는 호출 주체가 직접
`ANTHROPIC_API_KEY`를 채워야 한다(예: `.env`를 dotenv로 로드).

**검증**: 격리 후 로컬 `pytest -q` — **1.85초**(기존 27초대에서 복귀, 기존
5.98초 기준선보다도 빠름). 실제 키를 프로세스 환경에 주입한 상태로 다시
돌려도 **1.93초**로 동일 — 오염 경로가 있어도 네트워크를 타지 않음을
확인했다.

## 8. 로컬 환경 메모

CI(Python 3.12)와 로컬(Python 3.13) 차이로 걸린 것들:

- **`pip install -r requirements.txt` 가 로컬에서 실패한다.**
  `psycopg2-binary==2.9.9` 가 Python 3.13 휠을 제공하지 않아 소스 빌드하다 막힘.
  CI는 3.12라 정상. 필요한 패키지만 개별 설치하면 된다.
- 개별 설치한 것: `ruff`, `black`, `langgraph`, `sqlalchemy`, `alembic`,
  그리고 `psycopg2-binary` — **단 2.9.9 가 아니라 2.9.12 다.** 3.13 휠이 있는
  최초 버전이라 이걸로 올렸고, `requirements.txt` 의 핀은 건드리지 않았다.
  즉 로컬은 requirements.txt 와 다른 버전으로 돌고 있다(2026-08-23 기준).
  나머지 패키지도 개별 설치라 핀에서 벗어나 있다(예: fastapi 0.141.1 vs 핀
  0.115.0, pytest 9.1.1 vs 핀 8.3.3) — 로컬 통과가 CI 통과를 보장하지 않는다.
- **Python 버전 기준이 세 갈래로 갈려 있다** — 인수인계 메모는 3.11, CI
  설정(`.github/workflows/ci.yml:51`)은 3.12, 실제 로컬 venv는 3.13.9.
  3.11 은 이 개발 PC에 설치돼 있지 않다. 어느 것을 기준으로 삼을지는 팀 확인
  대기 중이며, 그때까지 위 이탈 상태로 작업한다.
- DB 테스트는 `DATABASE_URL` 이 없으면 자동 skip된다 (정상). 실측 15개
  (`conftest.py` 의 `with_db` fixture 사용분).
- **단 CI 는 skip 하지 않는다.** `ci.yml` 이 postgres 서비스 컨테이너를 띄우고
  `DATABASE_URL` 을 주입한 뒤 `alembic upgrade/downgrade/upgrade` 왕복까지
  돌린다. 그래서 CI 는 **401 passed, skip 0** 이고 로컬은 386 passed / 15
  skipped 다 — 차이 15개가 곧 DB 테스트다. 로컬에서 통과했다고 DB 경로가
  검증된 것이 아니다.
  (`db/base.py:8` 의 "DATABASE_URL이 없는 환경(지금 CI가 그렇습니다)" 주석은
  family_graph PR에서 CI 에 DB 가 추가되면서 사실과 달라졌다 — 별건으로 정리 필요)

#### ⚠️ `.env.example` 을 그대로 복사하면 테스트 3건이 실패한다

`copy .env.example .env` 를 하면 `DATABASE_URL=postgresql://postgres:devpass@
localhost:5432/family_assets` 가 설정된다. 로컬에 Postgres 가 떠 있지 않으면
`with_db` 를 쓰지 않는 `test_health.py` 의 3건(`test_chat_default_route`,
`test_chat_routes_to_decedent_estate`, `test_chat_routes_to_tax_calculator`)이
skip 되지 않고 접속을 시도하다 `sqlalchemy.exc.OperationalError` 로 실패한다.
접속 타임아웃 때문에 스위트 실행 시간도 늘어난다.

실측(2026-08-23):

| `.env` 상태 | 결과 | 소요 |
|---|---|---|
| `DATABASE_URL` 설정됨, Postgres 미기동 | 3 failed, 383 passed, 15 skipped | 78초 |
| `DATABASE_URL` 주석 처리 | **386 passed, 15 skipped** | 1.7초 |

Postgres 를 띄우지 않고 작업할 때는 `.env` 의 `DATABASE_URL` 을 주석 처리하는
쪽이 낫다. 실패 3건을 "원래 깨져 있는 것"으로 오해하기 쉬운 함정이다.

CI 에서는 같은 변수가 반대로 동작한다 — 거기엔 실제 postgres 가 함께 떠 있어
`DATABASE_URL` 이 있어야 정상이다. 즉 "설정하면 안 된다"가 아니라 **"DB 없이
설정만 하면 안 된다"** 가 정확한 규칙이다.

## 9. 유언장 사진 판독 1단계 (2026-08-25)

### 배경

유족·어르신 대상 서비스에서 유언장 전문을 타이핑하는 것 자체가 진입 장벽이라,
사진을 올리면 판독해 입력을 채워주는 기능을 만들었다. **사전 조사에서 확인된
가장 중요한 제약**: Anthropic Messages API는 이미지(JPEG/PNG/GIF/WebP)와
PDF는 받지만 오디오는 지원하지 않는다(공식 문서 확인 + SDK 저장소의 오디오
지원 요청 이슈가 "Closed as not planned"로 닫혀 있음, 2026-08-25 확인).
**녹음 유언은 이번 기능 범위 밖 — 기존 대본 텍스트 입력을 그대로 유지한다.**

### 설계 방침 (전부 결정된 채로 받음)

- **A. 판독은 입력 보조, 판정이 아니다** — 애매한 값은 되묻고, 확정된 값으로
  기존 룰베이스 판정을 그대로 돌린다.
- **B. 파일은 저장하지 않는다** — 판독 후 즉시 폐기. `DecedentState`에
  이미지 필드를 두지 않아 구조적으로 막았다(#15가 유언장 원문을 배제한 것과
  동일한 방식).
- **C. 마스킹 원칙에 예외 명시** — `CLAUDE.md` 절대 원칙 4에 예외 조항 추가
  (이미지는 읽는 행위 자체가 전송이라 사전 마스킹이 불가능함을 근거로 기록).
- **D. 사용자 사전 고지** — 업로드 전 "외부 AI 서비스로 전송됨 / 저장 안 함 /
  주민등록번호·전화번호·계좌번호는 가리기 권장(강제 아님) / 성명·주소·날짜는
  가리면 안 됨"을 노출. 강제하지 않는 이유: 판독 결과 텍스트에 기존
  `mask_text()`가 이중 방어로 걸리기 때문.
- **E. 확신도 3단** — high(즉시 채움)/low(확인 질문)/none(직접 입력 유도).
- **F. 자서는 반드시 확인 질문** — 필적 감정 영역이라 LLM이 판정하면 안 됨.

### 구현 요약

**기존 판정 로직(requirement_checker.py/masking.py/result_formatter.py/
recording_checker.py)은 단 한 줄도 안 고쳤다** — 판독값을 "유언자: OOO" 같은
텍스트로 재구성해 `payload.user_message` 자리에 대신 넣는 방식으로, 기존
텍스트 입력 경로를 그대로 재사용했다(방침 A를 문자 그대로 구현). 부수 효과로
날인(seal)은 기존 `seal_answer` user_confirm 메커니즘을 그대로 재사용했고,
자서(handwriting)도 이미 `extraction_type: "user_confirm"`이라 새로 만들 것이
없었다 — 방침 F는 사실 기존 동작과 이미 일치했다.

### 실측 확인 (mock 기반)

- 전부 high-confidence → 질문 없이 즉시 판정 (자서 제외)
- low-confidence 1개 → 요건 판정을 미루고 사진 확인 질문 먼저 → "예" 답변 시
  다음 턴에 판정 완료, "아니요" 답변 시 그 필드는 버려지고 사용자가 그 턴에
  직접 입력한 텍스트를 기존 정규식이 그대로 재탐색
- none-confidence → 확인 질문 없이 조용히 absent (기존 `address_envelope_check`
  같은 후속 followup으로 자연히 이어짐을 실측 확인)
- 자서는 고신뢰도 케이스에서도 항상 PENDING으로 남아 직접 질문 (LLM 미판정 확인)
- 이미지 데이터가 응답(`AgentOutput`)·`photo_draft`·세션 저장 경로 어디에도
  없음을 직접 검증 (`test_decedent_photo_intake.py`, `test_orchestrator.py`)

### 🔴 실제 이미지 검증 — 완료 못 함 (API 키 인증 실패)

PIL로 만든 텍스트 이미지로 실제 API 호출을 시도했으나 `AuthenticationError`.
기존 텍스트 함수(`extract_will_date`)로 교차 검증해도 동일하게 실패해, **새
코드의 문제가 아니라 키 자체가 지금 인증을 통과 못 하는 상태**임을 확인했다
— §0-1 참고. 코드 자체는 mock 기반 단위/통합 테스트(11+12+2=25개)로
파싱·전송 구조·확신도 분기·자서 예외·이미지 미저장을 전부 검증했지만, 실제
Anthropic 응답 품질(사진을 정말 잘 읽는지)은 키 문제가 해결되면 재검증이
필요하다.
